# Backend — Plantry

Go binary (module `github.com/jaltszeimer/plantry/backend`). Must cross-compile to ARM with no CGO — use `modernc.org/sqlite` (pure Go), never `mattn/go-sqlite3`.

## Commands

All commands run from `backend/`:

```bash
go build ./...                        # compile
go test ./...                         # all tests
go test -run TestName ./path/...      # single test
go vet ./...                          # vet
golangci-lint run                     # lint
sqlc generate                         # regenerate from queries + schema
go test ./pkg -run TestName           # the edit loop: no race, test cache on (never -count=1)
scripts/check-sqlc-usage.sh           # every sqlc query needs a non-test caller
go tool deadcode -test ./...          # unreachable functions (pinned x/tools); the gate ignores sqlcgen/
go run ./cmd/plantry backup -out F    # consistent copy of the database + secret.key (see Backup)
```

`go tool deadcode -test ./...` must report nothing outside `internal/adapters/sqlite/sqlcgen/`; `scripts/gate.sh` and `backend.yml` run it, with the tool version pinned in `go.mod`. Remove the dead function instead of keeping it. The gate also cross-builds `GOOS=linux GOARCH=arm64` and `GOARCH=arm GOARM=7` (`CGO_ENABLED=0`), so a CGO or arch-specific dependency fails there.

The race detector runs once per PR in the repo-root `scripts/gate.sh` (`go test -race -short -gcflags=modernc.org/sqlite/...=-race=false ./...`) and in CI; see "Test speed contract" in the root `CLAUDE.md`. **Test databases** come from `testhelper.NewTestDB` (a copy of a migrated template), `NewTestDBFrom(t, testhelper.SnapshotDB(t, db))` for a fixture built once per process, or `DSN`/`DSNWith` for a test that opens its own file: they turn fsync off. A test that is slow by nature calls `testhelper.Slow(t, reason)` and is listed in `test-budget.json`.

`scripts/check-sqlc-usage.sh` fails when a `-- name: X` in `internal/adapters/sqlite/queries/*.sql` has no `.X(` in a non-test `.go` file outside `sqlcgen/`. It runs in CI and in the repo-root `scripts/gate.sh`; delete the query instead of keeping it unused.

## Architecture — Hexagonal-Lite

Data flow: `transport → domain ← adapters`

**Aggregates** are plain exported structs. `*.Service` holds business logic and takes repo interfaces as constructor args — never concrete types.

**sqlc workflow:** edit `queries/*.sql` → run `sqlc generate` → implement/update `*_repo.go` using generated functions. Never write raw SQL outside of query files.

**Safe table rebuild.** Dropping a table with foreign keys on cascade-deletes its dependants (00014/00016 did on old installs). Rebuild tables (e.g. to add `AUTOINCREMENT`, as 00030 for `plates`/`cook_sessions` and 00033 for `presets`) in a Go migration registered with `goose.AddMigrationNoTxContext`: pin one connection with `db.Conn`, `PRAGMA foreign_keys = OFF` on it, copy in one transaction, run `PRAGMA foreign_key_check` before commit, restore `foreign_keys = ON` afterwards, and recreate triggers the drop removed. Give sqlc the end-state schema in `db/schema_patches/`.

**Migrations** use goose. Numbered SQL files in `db/migrations/`. Go migration files (`.go`) handle complex data transformations. Migrations run automatically at startup (`goose.Up` in `main.go`) — no manual step needed.

**Secret key.** `config.EnsureSecretKey` runs at startup. If `PLANTRY_SECRET_KEY` is set it wins and no file is written. In Docker the `/data` volume holds both the DB and the key; losing the key makes stored API keys undecryptable. `crypto.NilCipher` exists only for tests.

The profile (`domain/profile`) also carries `diet_type`, `meat_days_per_week_max` and `household_portions` (00023), and (00045) the nutrition goal `goal` (`maintain` default / `lose` / `gain`; absent in `PUT /api/profile` keeps the stored one) and optional body data `weight_kg`, `height_cm`, `birth_year` (a year, not an age: it does not go stale), `sex` (`female`/`male`/null) and `activity_level` (PAL 1.4 / 1.6 / 1.8). They are a full replace (null clears), validated in `profile.validate` (`error.profile.invalid_goal`, `invalid_body_data`); a `kcal_target` below `profile.MinDailyKcal(sex)` (1500 for male, else 1200, also with an unknown sex) is `error.profile.kcal_below_floor` on every save (reading a stored lower target still works; the user raises it to save). The kcal target stays the user's own number; the "suggest my target" estimate (Mifflin-St Jeor x PAL) is computed in the frontend (`lib/nutrition-estimate.ts`).

**Nutrition policy** (`planning/policy.go`, `PolicyOf(planning.Profile)`): the one place for the kcal tolerances, replacing the old `KcalBandLow/High`. Day band (S2) / week band (S4): maintain 90-110 % / 95-105 %, lose 90-105 % / 95-103 %, gain 95-110 % / 97-105 % of the scaled target (the lose/gain week bands and the day band widths are professional-practice inference; sources in the code comment). Floor (hard rule **H9** `kcal_below_floor`, `index.h9`): a complete day with a plate of the target, nutrition data and a kcal target must hold at least `max(75 % x scaled target, absolute floor x planned/all meals)` kcal per eater; the absolute floor (1500 male, else 1200, secondary sources) scales with the planned meals like the target, less routine cells that hold no plate (`DayKcal.Share`; such a cell leaves the scaled kcal and protein target too, like a No-plate cell, B1 of #150). On the board H9 shows only from today on and as a warning on days without a draft plate (`BoardIssues`). **Day away** (spec v1.1 SB3/SF4): a day with no slot planned (every active cell `none` or a `routine` without a plate) is `DayKcal.Away` (set in `index.dayAccounts`, so board, planners, dry runs and eval agree) and `DayEval.away` (compact: only when true); H9, S2, the day S3, the heuristic's top-up passes and `kcalNote` skip it, and it is left out of `Evaluation.Week` like an incomplete day. A day with any non-routine meal left (a planned breakfast) is judged on its planned part (`TestEvaluate_PlannedBreakfastLeftIsStillJudged`); a routine-only day (every lunch and dinner away, none or an unplated routine and only routines left, e.g. a routine breakfast with lunch and dinner away; a plated routine lunch or dinner is food at home and keeps the day judged, `TestEvaluate_AllRoutineDayWithAPlatedRoutineDinnerIsJudged`) is judged like a fully away day: `dayAccounts` leaves it out, so no floor, no H9, no range, no under-minimum line and no lever offer, and it leaves the week (spec v1.5 SB3, V63 c; `TestEvaluate_RoutineOnlyDayIsNotJudged`, replacing #172's routine-breakfast-judged rule). An `away` op also clears the stored light or filling mark of the lunch or dinner it takes off the plan (`unmarkAway`, saved with the call's light, so Undo restores it). H9 is in `Check`, in the board's issue filter (H1, H2, H5, H8, H9), in the repair feedback (`repair.go`) and in `Score.HardViolations`. **Weekly ledger**: `Evaluation.Week` (`{days, avg_kcal, target_kcal, pct}`: the complete days S2 judges, average kcal against the average scaled target; nil without a target or such a day) is in the run log's `plan.evaluation`, the compact `evaluate_plan` / `get_plan` result (whole window, never narrowed to the touched days) and `apply_changes` `after.week`. Soft issue S4 `week_kcal_below_band` / `week_kcal_above_band` (no date, no options) needs at least 3 complete days. The prompts say it with `Policy.Describe()`: the target is a target, the week matters most, the floor is hard (planner prompt `p10`, chat prompt `v11`). **Protein and macros (00046, planner `p11`, chat `v12`, heuristic `h10`)**: with `weight_kg` the protein target is g per kg (`Policy.ProteinGPerKg`: maintain 1.0, lose and gain 1.6, at least 1.0 from age 65 (also over a lower override, which is raised to 1.0), optional profile override `protein_g_per_kg` validated 0.8-2.2 (2.2 is an unverified upper bound), never below the DGE 0.8; sources in the `policy.go` comment), scaled to the planned part of the day like the kcal target (Slot bands) (`DayEval.protein_target_g`); a day under 90 % of it is S3 `protein_below_target` (params `protein_g`, `target_g`, `min_g`; its options must raise the day's protein grams), replacing the share margin; without a weight the `ProteinPct` share logic is unchanged. `Evaluation.Week` also carries `avg_protein_g`, `target_protein_g`, `protein_pct`, `carbs_pct`, `fat_pct` (kcal-weighted) and `fiber_g` (average per day, display only, DGE 30 g; absent when no food has fibre data or any food on the counted days lacks it, since a missing fibre value reads as 0 and a partial average would mislead). With 3+ complete days: S3 `week_protein_below_target` (average under 100 %) and soft S5 `week_carbs_out_of_range` / `week_fat_out_of_range` (AMDR carbs 45-65 %, fat 20-35 % of energy, or the user's `carbs_pct` / `fat_pct` +-5 points), no date, no options; S5 applies to every user (it does not depend on the weight) and ranks last, after preferences and never at the cost of kcal or protein. Heuristic `closeProteinGaps` (after the floor pass, needs a kcal target and a weight): one verified no-cook add per day under 100 % of the day target (S3 day issue stays < 90 %; the day caps of the heuristic below hold), no food twice a day, the most protein first (adds that stay at or under the day target first), with diet type, the day band, the running week average under the week band top and every hard rule checked by `verify`; a day nothing lifts gets the run note "Protein below target". **Light intent (planner `p12`, chat `v13`, heuristic `h11`; `planning/light.go`)**: a light request is structured data, a list of `{date, scope: meal|day, slot?: lunch|dinner}` (`planning.LightIntent`, `ValidateLight`), not free text. The intents are stored per date in `plan_light(date, scope, slot)` (migration 00047, sqlc `plan_light.sql`, `sqlite.PlanLightRepo` = `planning.LightStore`) and `Builder.Build` loads the window's rows into `State.Light`, so the board, the chat prompt/`chatView`/`get_plan`, `evaluate_plan` and every run (the HTTP heuristic regenerate too) stand under them without being told again; every `plan.evaluation` step carries them (`Evaluation.light`), the run's `scope_json` and `plan.context` list the request's own. A call that is given `light` merges per date **and slot** (`MergeLight`, C7): a meal intent replaces only the stored meal intent of its date and slot, a day intent the date's day intent; `scope: none` with a slot clears that slot's meal intent, without one the whole date (the chat tools' clear shape); everything else stored stays. `apply_changes` `saveLight` merges with the stored rows the same way. Input: `submit_plan` / `evaluate_plan` `light`, chat `apply_changes`, `get_plan` and `regenerate` `light` (a tool-call ctx value merged over the stored ones by `evalWindow`), `planning.Request.Light`. Saved: a successful planner run writes the effective light of its window (`merged.Light`, inside the save transaction) and a non-dry-run `apply_changes` writes its own (`saveLight`); past dates are pruned on every write (`LightStore.Replace`). Rejected back to the model (`ResolveLight`; tool error `ErrInvalidInput`, or the chooser's repair feedback): a date outside the window, a `meal` slot the plan has no slot for (custom slot names), and more than `MaxLightDays` (3) day-scope intents in a window once merged with the stored ones (the message points to the profile goal `lose`); meal intents are not capped. Run notes echo the light in plain words in the notes' language (`lightNote`: "Light: Tue dinner, Thu day" / "Leicht: Di Abendessen, Do Tag"). The tool schema is one definition, `planning.LightSchema(withClear)`. A light day's target is clamped at the floor in `DayKcals` (a lose-mode target of 1600 asks for 1500, not 1360, so S4 is not raised by a day held at the floor); S6 is not raised on confirmed plates or routine cells. **`meal`**: that lunch or dinner holds at most 75 % (`LightMealShare`) of its normal share (the slot's expected share of the day's full target, `DayKcal.mealShare`: see Slot bands, no longer an even split); soft issue S6 `meal_not_light` (params `kcal`, `max_kcal`, `normal_share_kcal`) when it is not lighter. **A meal intent shifts the day's target (planner `p16`, heuristic `h15`)**: for every light meal of a day the target moves by `-(1-LightMealShare) x normal share` (-25 % of the meal's share), for every hearty one by `+(HeartyMealShare-1) x normal share`; the sum is capped at the policy day band (`Policy.shiftedTarget`: no lower than `DayLow x Scaled`, no higher than `DayHigh x Scaled`, so maintain 90-110 %, lose 90-105 %, gain 95-110 %). The shifted value is `DayKcal.Adjusted`: the S2 band is centred on it, `DayEval.target_kcal` is it and `normal_target_kcal` the normal one, `Week.target_kcal` the average of the shifted targets, and the heuristic's top-up passes (which read `Adjusted`) aim at the shifted band. **H9 does not follow the shift** (research: the safety floor is measured against the normal target even on an explicit eat-less day): `DayKcal.Floor` is 75 % of the scaled normal target for meal, day and unshifted days alike, and the absolute floor (1200 / 1500, scaled by the share) never moves; the H9 issue carries `target_kcal` (normal) and, when the day is shifted, `shifted_target_kcal`; a day intent wins over meal intents on the same day. The protein target does not move; S6/S6b are unchanged. Two light meals of three on a 2200 kcal day (breakfast 310): shift -16.7 % capped to -10 %, target 1980, band 1782-2178, floor stays 1650; lunch at its light cap 550 needs a dinner of at least 790, over its own light cap, so S6 soft remains and H9 holds (`TestMealShift_Reference*`). To eat less for a whole day the user uses scope `day`. **`day`**: the day's target is 85 % (`LightDayShare`, `DayKcal.Adjusted`) and its S2 band is centred there (`DayEval.target_kcal` is the adjusted one, `normal_target_kcal` the normal one, `light` is `meal|day`); H9 and the absolute floors stay on the normal target. `Week.target_kcal` is the average of the adjusted day targets (S4 measures against it, so honouring the wish does not raise S4), `Week.normal_target_kcal` the normal average (only when it differs). Both prompts say it with `Policy.Describe()`: light means `meal` unless the user explicitly asks to eat less for the day or week, never below the floors, say so in the reply when a floor stopped a lighter day. Heuristic: a light cell ranks recipes over its reduced share last, takes a side only while the plate stays within the share, never grows or adds to a light meal's plate (`editablePlates`, `topUpDay`) and the other meals of a light-meal day are topped up to the day band's low end. The HTTP generate/regenerate bodies do not take `light` yet; the board shows the light marks (see Plan window and read models).

**Hearty (planner `p16`, chat `v18`, heuristic `h15`; migration 00050).** `LightIntent.level` is `""` (light, the default every older row and call keeps) or `hearty`; `plan_light.level TEXT NOT NULL DEFAULT 'light'` stores it (the repo writes `light` and reads it back as `""`). A hearty `meal` holds at least `HeartyMealShare` (125 %) of its normal share and raises the day target by 25 % of that share (capped at the day band, see Light intent); soft S6b `meal_not_hearty` (params `kcal`, `min_kcal`, `normal_share_kcal`) when it holds less. A hearty `day` targets `HeartyDayShare` (115 %) with the band centred there (`DayKcals`). `MaxLightDays` counts light and hearty day intents together. The heuristic's `kcalShare` ranks a hearty cell's recipes by their fit to the raised share. `DayEval.light_level`, `planview.Day.LightLevel` and `/api/plan` `days[].light_level` are `hearty` for a hearty request (omitted for light); run notes say "Hearty: ..." / "Deftig: ..."; `LightSchema` has `level`.

**Slot bands (spec v1.1 SB1-SB3, NU11; migration 00053).** Every time slot has an energy band, `time_slots.band_min_pct` / `band_max_pct` (both NULL: the default of `slot.DefaultBand`, by name, else by kind: breakfast 20-30, lunch 30-40, dinner 25-40, snack 5-15, custom light 5-15, custom meal 25-40; both set otherwise). `slot.Service`: `Bands` (effective bands of the active slots in sort order), `SetBands` (atomic; validates the whole effective set: each 0-100, min at most max, minimums add up to at most 100 and maximums to at least 100, else `domain.ErrInvalidSlotBands`, `error.slot.invalid_bands`, text with the numbers; a refusal changes nothing), `ApplyPreset` (`lunch_biggest`, `dinner_biggest`; the default is not a preset); creating or updating a slot never touches or refuses a band. HTTP: `GET` and `PUT /api/settings/slots/bands` (`{items:[{slot_id,min_pct,max_pct}]}`, GET adds `shares` in percent), `POST /api/settings/slots/bands/preset {name}`; the slot list carries `band_min_pct`, `band_max_pct`, `band_custom`. **Expected share** (SB2, `slot.Shares`): band midpoint over the sum of the midpoints of the active slots (27.0 / 37.8 / 35.1 % with the defaults); `Builder` puts it in `State.SlotShare` and the bands in `State.SlotBand`, and every rule that needs "the meal's share" reads it: `DayKcal.Share()` is 1 minus the shares of the slots not planned (marked away, default no plate, routine without a plate; SB3), so the planned part's target, floor, protein target and the S2 band prorate by it; `DayKcal.mealShare(slot)` is the slot's share of the day's full target, the base of a light meal's cap (0.75 x) and a filling meal's minimum (1.25 x) and of the meal-mark shift of the day's target; the heuristic's per-meal aim (`kcalShare`) is the same figure; a state without bands splits evenly as before. `DayEval` carries `away_kcal` (full target x the unplanned shares) and `planned_target_kcal` (target less it) on a day with a slot not planned; a fully away day is still not judged. **S10 `meal_outside_slot_band`** (`slotBandIssues`, soft, no options, priority 7, not on the board): a lunch or dinner plate on a complete, non-away day whose kcal per eater are outside its band in percent of the day's full target; a meal with a light or hearty mark (or on a light or hearty day) is exempt. Settings → Meals & week shows the bands with the running sums and the two presets (`SlotBandsEditor`).

**DGE weekly food rules (soft S7; `planning/groups.go`, `diet/group.go`).** Source: DGE "Gut essen und trinken" 2024 (meat and sausage at most 300 g per week, fish 1-2 times, legumes at least once, 5 portions of fruit and vegetables per day). `diet.GroupOf(leaf name)` derives meat (incl. sausage and ham), fish (incl. seafood) or legume with the same folded en/de keyword matching as `diet.Classify` (phrases cut out look-alikes such as Hühnerei; a vegan/vegetarian/pflanzlich/plant-based/meat-free marker makes the name none). Seasonings are none: broths and stocks (Brühe, Fond, stock, broth, bouillon), animal fats and oils (Schmalz, Fett, Öl, Lebertran), fish and oyster sauces, gelatin, Worcestershire sauce; "Gemüsebrühe mit Huhn" is still meat. Legumes: beans (not green beans), lentils, chickpeas, peas (Erbsen count, as the DGE lists them), tofu, tempeh, edamame, hummus, falafel, cannellini/borlotti; peanuts (Erdnüsse), soy sauce and soy drinks, Bohnenkraut, coffee/cocoa/tonka beans and pea protein (Erbsenprotein, an isolate) do not. Fruit and vegetables are the leaves of the produce shop section (override or `shopping.Classify`), potatoes excluded. `food.Detailed.Leaves` flattens a recipe into leaf grams per portion; `FoodFacts.Groups` holds the group grams per portion (leaf: 100 g). `Evaluation.Week` gains `meat_g` (per eater: the real sum over the counted complete days, `week.days`), `fish_meals`, `legume_meals` (plates with at least 50 g of fish or legumes per eater on those days) and `produce_g_per_day` (display only: portion grams are too uncertain for an issue). With 5+ complete days, soft S7 issues without date or options: `week_meat_above_dge` (over 300 x days / 7 g; not for vegetarian/vegan/pescetarian), `week_fish_below_dge` (0 fish meals; not for vegetarian/vegan), `week_legumes_below_dge` (0). ## Availability

Migration `00024_availability.sql`, package `domain/availability`. A cell is (date, slot) and its mode is `plan`, `routine` (needs a `preset_id`; a label only for now, nothing applies the preset) or `none` (No plate). It resolves as per-date override → weekday default (weekday 0 = Monday) → `plan`. `plan` defaults are never stored.

- `GET /api/availability?from=&to=` — resolved cells with `source` (`override` / `default` / `fallback`), at most 62 days.
- `GET` / `PUT /api/availability/defaults` — `{items: [{weekday, slot_id, mode, preset_id}]}`; PUT replaces the defaults of all active slots.
- `PUT /api/availability/{date}/{slotId}` — `{mode, preset_id?, note?, remove_plate?}`. `none` on a cell with a plate is `409 error.availability.cell_has_plate` unless `remove_plate` is set; then the override is written and the plate removed through `plate.Service.RemoveMealsAt` in the same unit of work (`availability.SetOverrideMeals`; `SetOverride` keeps the old signature for the agent and the re-plan), and the response `{cell, removed, also_changed}` carries the `PlanSnapshot` that restores it (`POST /api/plan/restore`; `removed` is null when nothing was removed) and the batches whose cook moved (R1, see Sessions and D11). `DELETE` clears the override.
- `POST /api/availability/away?today=` — `{cells?: [{date, slot_id}], date?, note?}` (`availability.SetAway(ctx, AwayInput{Cells, Date, Note, Today})`): one unit of work writes `none` overrides on the cells (`date` alone: every active slot of that date whose mode is not `routine`; a cell that already has a `none` override keeps its note unless `note` is given) and removes their plates through `RemoveMealsAt`. Response `{cells, before: [{date, slot_id, override|null}], removed, also_changed}`; undo is `RestoreOverride` of each `before` then `Apply(removed, Restore)`. A cell before `today` is `400 error.plan.past_cell` (`domain.ErrPastCell`); neither `cells` nor `date`, or a bad date, is `400 error.invalid_body`. Confirmed plates: the HTTP path is the user (no guard), the agent path is guarded by the plate service.

A cell holds at most one plate: migration `00025_plates_cell_unique.go` turned the old per-plate skip flag into `none` overrides (with its note), merged duplicates, dropped the flag column and made `(date, slot_id)` unique. Creating or moving a plate into a `none` cell is `409 error.plate.cell_unavailable`; into an occupied cell, `409 error.plate.cell_occupied`. The agent sees `none` and `routine` cells and must not plan them.

## Plan window and read models

Package `domain/window` (pure): a window is the 7 days starting on `plan.shopping_day`. `Containing(date, sd)` starts on the latest shopping day ≤ date; `Anchored(today, anchor, sd)` is the window containing today (`today`) or starting on the first shopping day ≥ today (`next_shopping_day`).

Package `domain/planview` builds the read models; it never writes and takes its dates as arguments. Plates load with one `ListByDateRange` call for the whole range and sessions with `CookSessionRepo.ListInRange` (two queries), never per plate.

- `GET /api/plan?start&today` — the window at `start` (must be a shopping day, else `400 error.plan.invalid_start`) or the anchored one: `window`, active `slots`, `cells` (date × active slot with availability and plate), `sessions` (cooking in the window or linked to a plate in it), `days` (per-eater macros with `complete`/`missing`), `targets` (null without a kcal target), `stats`, `issues` (`planning.Check` over every cell of the window, filtered to H1, H2, H5 and H8, with diet classes from `food.Service.DeriveDiet`; `missing_plate` only while the window has drafts and only for cells dated today or later), `draft` (`{plates, sessions, run_id, notes, chooser}` of the newest run with drafts in the window, read through the `RunNotes` port; null without drafts) and `running_run_id` (from the `Progress` port; null while none is wired). The state for `planning.Check` uses the planner's row mappers (`planning.StatePlate`, `StateSession`, `StateCell`, `StateProfile`, `BaseFacts`, `ReadSettings`), so the board and the generator check the same state (`TestStateParity_BoardAndBuilder`). Only while the window has drafts does H8's candidate list load: the recipes not eaten since `planning.VarietySince` (sqlc `ListUneatenRecipes`, one query), with diet classes only when `planning.DietRestricts` the profile's diet type. Day macros resolve in one `PerPortionDetailedMany` batch, and the plate foods' nutrition from that batch also feeds the check state (`planning.WithNutrition`, with `SlotNames` and the stored light), so H9 and the soft rules see real macros. **Week ledger**: the board runs `planning.Evaluate` once over that state (`planview.evaluate`) and takes from it the hard `issues` (`planning.FilterBoardIssues`), `soft` (`planning.BoardSoftIssues`: S2-S7 without options, dated ones from today on, severity `soft`, apart from `issues`), `week` (`Evaluation.Week`, null without a kcal target or under `planning.MinWeekDays` = 3 complete days) and per `days[]` entry `target_kcal` (after a light request; null without a target), `light` (`day` or `meal`, omitted otherwise) `light_slot` (`lunch`/`dinner` of a light meal) and `light_level` (`hearty`, else omitted). `TestStateParity_BoardLedger` pins it to the builder's state.
- `GET /api/today?date&today` — confirmed rows only (D26); `verdict` (`draft_only` when the date has no confirmed plate and the window has drafts, `no_plan`, `no_plates`, `cook`/`quick_cook` for the uncooked main with most portions, ≤ 20 min is quick, else `nothing_to_cook`), `cook`, `meals`, `reminders` (`defrost`, `use_by`), `rate`, `plan_banner` and `setup`.
- `today` defaults to the server's local date; `date` defaults to `today`.

## Unit of work

`domain.Transactor` (`domain/transactor.go`, D21) is the port; `sqlite.TxRunner` (`adapters/sqlite/tx.go`) implements it. `InTx(ctx, fn)` runs `fn` in one transaction whose `*sql.Tx` travels in `fn`'s ctx, and every repository called with that ctx joins it. A nested `InTx` joins the outer one: there are no savepoints, so a failed nested call leaves its partial writes in the outer transaction and the caller must return the error. Multi-write operations (plate mutations, availability `none` with `remove_plate`, preset apply) run inside one `InTx`, and so do the `/api/plan` and `/api/today` read models, so a concurrent write cannot tear them.

**Statement cache.** Every repository resolves its queries through `conn.dbtx` (`tx.go`): outside a transaction a per-repository cache of statements prepared on the pool (`stmts`), inside one the unit of work's own statements, prepared once per transaction (from the pool statement through `Tx.StmtContext` when there is one, else on the transaction; never on the pool, whose only connection the transaction holds). Multi-statement strings and more than 256 texts run unprepared. Parsing the same SQL again on every call was 18% of the agent's CPU.

**State memo.** `planning.Builder` with `BuilderDeps.Version` (`sqlite.DataVersion`, wired in `main.go`, `testsvc` and the eval env) returns a deep copy (`deepCopy`, reflection, so new fields are copied too) of the last `State` it built for the same arguments while the data version is unchanged: the connection's `total_changes()`, `PRAGMA data_version`, a random per-connection id in a temp table, and the unit of work (a rolled-back write does not move `total_changes()` back, so a State built inside a transaction never matches outside it). With more than one open connection allowed there is no token and Build always builds. A chat tool call read the full state about ten times. `DataVersion` is hand-written SQL (sqlc cannot parse `PRAGMA` or temp tables), like `ChatRuns`. Pinned by `TestBuild_MemoCopiesShareNothing`, `TestBuild_MemoSeesEveryWrite`, `TestDataVersion_*`.

Every domain sentinel's i18n message key lives in `domain.MessageKey` (`domain/errors.go`; the plate quantity sentinels in `plate.MessageKey`); the HTTP error map adds only the status, and the agent's tool errors use the same keys. A test fails when a sentinel in `errors.go` has no key or no status.

## Plate aggregate and write path

`plate.Service` (`domain/plate/service.go`, built with `plate.NewService(plate.Deps{...})`) is the single write path for plates, plate components and cook sessions. Handlers, the agent tools and preset apply/copy all go through it.

- A cell (date, slot) holds at most one plate. A plate has `eaters` (default: the profile's household portions) and ordered components; a component is a food with `portions` per eater, or for a leaf `amount` + `unit`.
- A composed component is linked to a cook session. Without a given `CookSessionID` a new component gets a fresh session at the plate's own cell. Mutators: `Create`, `Update`/`UpdateMeal`, `Delete`, `RemoveMeals`, `RemoveMealsAt`, `ClearRange`, `AddComponent`, `UpdateComponentQuantity`, `SwapComponent`, `RemoveComponent`, `Apply`, and the meal operations `MoveMeal`, `ReplaceComponent`, `MoveCook`, `CopyMeal` (see Meal operations).
- `RemoveMeals(ctx, plateIDs) (MealResult, error)` removes plates in one unit of work (a missing plate is `ErrNotFound`, nothing removed) and returns `MealResult{Removed PlanSnapshot, Plates, Sessions, AlsoChanged []AlsoChanged, Undo}`; `Delete` is `RemoveMeals` of one plate and keeps its `(PlanSnapshot, error)` signature. `RemoveMealsAt(ctx, cells)` is the same for the plates on cells being marked `none` and also tracks the batches cooking on those cells (with links), so a cooked-ahead one re-anchors. `AlsoChanged{session_id, plate_id (the meal now cooking), date, slot_id, what: "cook_moved", from_date, from_slot_id}` (`plate/anchor.go`) is collected by the tracker (`tracker.moves`); `ClearRange`, `RemoveComponent`, `SwapComponent` and `RemovePlates` re-anchor too but do not return it.
- `Delete`, `ClearRange` and session deletion return a `PlanSnapshot` that restores them; `Apply(snapshot, ApplyOptions)` writes one (D22). `Apply` decides every plate's placement before it writes anything, so a conflict (an occupied cell without overwrite, a duplicate cell in the snapshot) fails the whole call. Snapshot refs are strings (`"s1"`), snapshot components carry `sort_order`, snapshot plates an optional `plate_id`. Preset apply and copy-week build snapshots and call `Apply`.
- `DELETE /api/plan?from&to&slot_id` is slot-scoped (`ClearRange`). `DELETE /api/plates/{id}` is `RemoveMeals` of one plate and returns the `MealResult` body `{removed, also_changed, undo}`.
- **Position (00048).** Every component has `position` (`plate.Position`: `main`, `side`, `extra`; column `plate_components.position`, default `side`), the address of "the main" and "a side" on a plate; a plate has at most one main. Go migration 00048 adds the column and backfills per plate in component order (first composed main/standalone/role-less food = main, other composed foods = side except dessert/drink = extra, a leaf = side when its effective role is a side role, else extra); sqlc reads `schema_patches/00048_plate_position.sql`. **Write rule** (`plate/position.go`, `Service.resolvePosition`, every insert path: `Create`, `AddComponent`, `Apply`/restore, so planner and agent writes too): an explicit position is kept; an empty one is derived against the plate's components so far (`DerivePosition`: a main-like food on a plate that already has a main becomes `side`; leaf roles come from `Deps.EffectiveRole`, wired to `shopping.RoleOf`); an explicit `main` on a plate that has one is `ErrInvalidInput` + `plate.ErrSecondMain` (`error.plate.second_main`, 400, in `plate.MessageKey`). `SwapComponent` keeps the position. Snapshots (`SnapshotComponent.Position`, `omitempty`), plate events and `Revert` carry it, so undo and restore round-trip it; `planning.ToSnapshot` leaves it empty (derived). The plate component JSON has `position`; the component create body takes an optional `position`.

### Sessions and D11

A `CookSession` (`domain/plate/session.go`) says "food X is cooked at (cook date, cook slot), producing `portions`", with `frozen_portions`, `cooked_at` and a note. Components link to it as `fresh` (own cell), `leftover` (later within keep days) or `frozen`; links are ordered in cell order (date, slot `sort_order`, slot id; D12). `plate.BuildView` / `SessionView` add links, consumption and warnings (`leftover_before_cook`, `past_keep_days`, `deficit`, `frozen_deficit`; D13).

D11 (`plate.Sync`): when a change alters what a session's links consume, a session that exactly covered its links before still covers them exactly after; one with a surplus or deficit keeps its portions; frozen portions never exceed portions. The service tracks every session a mutation touches (`tracker`) and settles once at the end: a session without links is deleted, the others follow D11. Explicit edits (`SetSessionPortions`, `SetCooked`, `AddLeftovers`, `DeleteSession`) always win over D11.

**R1 re-anchor** (`plate/anchor.go`, pure `reanchor`, applied by `settle` through `reanchorSession` to every tracked session that is uncooked and still has links): an uncooked batch cooks at its earliest linked meal (D12), or earlier when **cooked ahead** (its cook cell came before every meal before the mutation, so nothing was eaten there; a session with no links before the mutation, such as a `cook_at` one, counts as cooked ahead), and never on a `none` cell. The tracker keeps each session's cook cell and link cells before the mutation (`tracker.prior`, recorded by `track` / `remove`). After D11: a cook cell that no longer holds a meal of the batch moves the cook to the earliest remaining meal unless cooked ahead; a cooked-ahead batch moves only when its cook cell resolves to `none`; `Apply` with `Restore`, and any `Apply` for the sessions its snapshot links by id (an overwrite's undo), also pulls the cook back to a meal before it, so a preset apply or copy-week leaves unrelated batches alone. The target is the earliest meal that is neither frozen nor before today (the caller's `plate.WithToday`, else the plate service's `Now`); with none the batch stays. A move is skipped when it would add a `past_keep_days` warning (R2, checked only). Cooked batches never move; each move is a session `update` event and an `AlsoChanged`. So `Delete`, `RemoveMeals`, `ClearRange`, `RemoveComponent` and `SwapComponent` (the component left its batch) re-anchor; a cell change through `Update` is `MoveMeal`'s local rule (below). `RemovePlates`' explicit `Move` map wins over the helper (`tracker.noMove`); `Keep` sessions are not settled. Freezing needs `plan.freezing_enabled` and a recipe not marked unfreezable (D14). `LeftoverCells` suggests the next cells for leftovers.

### Meal operations (slice 2b)

`plate/meal.go`. Each runs in one unit of work, writes plate events and returns `MealResult{Plates (the named plates after), Sessions (MoveCook), AlsoChanged, Undo}`. A source or target cell before the service's today is `domain.ErrPastCell` (400 `error.plan.past_cell`); today is the caller's (`plate.WithToday`: the chat turn's `withToday`, a plan run's, re-plan's or away call's request date), else the clock's, so one request has one today. The guard follows the caller's today with no bound (a stale tab or a crafted `today` can move writes onto really past days): the evaluation replays send frozen dates to a server on the real clock, so a bound would refuse them, and this is a single-user LAN app. A zero request today never overwrites a turn's (`WithToday` ignores it). Hand edits on confirmed rows are allowed; the agent stays under the draft guard. The agent reaches them through `apply_changes` (see Chat agent).

- **Local rule** (`localRule`, per batch a moved plate eats from; the session is then kept out of settle's re-anchor via `tracker.noMove`): when the cooking meal moved (against the tracked cook cell or the current one, a drop may have re-anchored it), the cook goes to the batch's earliest meal not before today, and a meal that becomes earliest takes the batch only if every meal stays within keep (`cookTarget`, `CheckLink`; frozen links within `plan.freezer_keep_days` count): otherwise that named meal cooks fresh and the cook goes to the earliest remaining meal (`became_cooking_meal` when it was not named); an earliest meal the caller did not name always gets the cook. When a named meal now comes before the cook, the cook re-anchors to it under the same keep check. Then every named meal the batch cannot feed (before the cook, past keep, or the batch is cooked) leaves it and cooks fresh at its own cell; D11 shrinks the batch. A meal the caller did not name never loses its dish. `AlsoChanged.What`: `cook_moved` (the cook moved to a named meal, or a removal re-anchored), `became_cooking_meal` (to a meal not named; `plate_id` is it), `cooks_fresh` (`plate_id` left `session_id`; `why` = `before_cook`, `past_keep_days` or `cooked`), `batch_resized` (D11 changed a named batch's portions; date/slot = its cook cell). A cook move of a batch whose meals are all named is not reported.
- **MoveMeal(plateID, to, Occupant{Kind, To})**: target not `none` (`ErrCellUnavailable`). A taken target needs an occupant: none → `*plate.OccupiedError{PlateID}` (wraps `ErrCellOccupied`; HTTP 409 with `occupant_plate_id`), `swap` (the occupant goes to the source cell, which must not be `none`; the two plates exchange eaters, so eaters stay with the cells), `to` (the occupant moves on to an empty cell; the source counts as free), `drop` (the occupant goes through `remove`, its batch re-anchors). Swaps park the occupant on `0001-01-01` inside the unit of work so the cell unique index holds; both moves are decided on the written state together. `UpdateMeal` (PUT) with a new cell is MoveMeal without an occupant; `Update` wraps it for the agent.
- **ReplaceComponent(plateID, Selector{Position main|side | ComponentID}, foodID, Source{SessionID | CookAt}, qty?)**: `side` needs exactly one side. Same food → `ErrInvalidInput`. Position and per-eater quantity are kept unless qty is given; the old batch is tracked (D11 + R1 re-anchor at settle, reported as `cook_moved`). `SessionID` links via `attach` (CheckLink = R2); `CookAt` creates a session there (not past, not `none`, on/before the plate's cell; counts as cooked ahead). The link is checked with freezing off (a replace never freezes a meal): past keep is the keep-time error (`ErrSessionPastKeepDays`). `SwapComponent` is `replace` with a fresh source.
- **MoveCook(sessionID, cell)**: uncooked batch, target not past (`ErrPastCell`) or `none` (`ErrCellUnavailable`), every meal on/after the target and within keep; else `ErrInvalidInput` naming the blocking plates. A move never freezes a meal: only a meal already frozen before (`Classify` against the old cook) may rely on the freezer, so a meal that would land past keep refuses the move.
- **CopyMeal(plateID, cells, leftover|fresh)**: copies components and eaters through `createPlate` (strict: a leftover copy is CheckLink'd per cell); any failing cell (occupied, `none`, past, out of keep) fails the call, prefixed with the cell. A leftover copy is checked with freezing off, so a cell past the keeping time fails even when freezing is on.
- **Undo** (`plate/undo.go`): `Undo{first_event_id, last_event_id, cells: [{date, slot_id, before, after}]}`. `Service.Recorded(ctx, fn)` runs fn in one unit of work and returns the event range it wrote (`EventLog.LastID` before/after; one unit of work writes contiguous ids). The meal operations, `RemoveMeals`/`RemoveMealsAt`, `UpdateMeal`, availability `SetAway` (with `cells`) and the plate-sheet component endpoints (via `Recorded` in the handler) return it. `availability.Service.Revert(undo)`: one unit of work; a cell whose slot no longer exists is skipped (nothing to restore); a cell whose override is not `after` → `domain.ErrPlanChangeStale` (409 `error.plan.change_stale`); then `plate.Service.RevertRange` (events by id range, `EventLog.Range`) → `RevertChecked` (shared with the agent's change undo: every event on those rows since the first must be in the set, `EventLog.CountAfter`, else `ErrPlanChangeStale`) → `Revert`; then each cell's override back to `before`. A token without events and cells is `ErrInvalidInput`.
- **HTTP** (thin, `handlers/meal_ops.go`; body `{plates, session_ids, also_changed, undo}`): `POST /api/plates/{id}/move` `{date, slot_id, occupant?: "swap"|"drop"|{date, slot_id}}`; `POST /api/plates/{id}/replace` `{position? | plate_component_id? (exactly one), food_id, session_id?, cook_at?: {date, slot_id}, portions? | amount?+unit?}`; `POST /api/plates/{id}/copy` `{cells: [{date, slot_id}], as}` (201); `POST /api/cook-sessions/{id}/move-cook` `{date, slot_id}`; `POST /api/plan/revert` `{first_event_id, last_event_id, cells?}` → `{plate_ids, session_ids}`. `POST /api/plates/{id}/components` also takes `cook_at: {date, slot_id}` for a composed food (`Service.AddComponentAt`: a new batch cooked there, the add of a `cook_at` alternative; a leaf or a `cook_session_id` with it is `400`). `PUT /api/plates/{id}` and the component endpoints keep their plate body and add `also_changed` and `undo`; `POST /api/availability/away` adds `undo`. **`?dry_run=1`** on `move`, `replace` and `POST /api/availability/away` runs the same call through `domain.DryRun(ctx, tx, fn)` (`transactor.go`: the unit of work is always rolled back, `plate.Service.DryRun` / `availability.Service.DryRun`, handler helper `orDryRun`) and returns the body it would have written, `also_changed` included: nothing is kept and its `undo` token must not be used. Every other endpoint ignores the parameter and writes (`PUT /api/plates/{id}?dry_run=1` is a real update). The board's also-changed preview calls it first (`TestMealHTTP_DryRunPreviewsWithoutWriting`: no event, no session and no override is left behind).

## Units and rounding

`domain/units` (`round.go`): `Display(amount, unit)` rounds an exact amount for reading (D26). Metric mass/volume work in g/ml, rounded to 1 below 100 and to 5 from 100; from 1000 they switch to kg/l only for clean multiples of 100 (1500 g becomes 1.5 kg, 1235 g stays). tbsp/tsp round to 0.5; everything else, counts included, stays exact. `ToBase` converts metric units to g/ml so sums add up. `Buy` rounds a count unit up to whole units. `CountGrams` is the only count-to-gram table. Amounts are stored and summed exact; round only for display.

## Food history and list filters

Eating history is derived, never stored (D16): `food.Service.Derive(ctx, today, foods...)` sets `LastEaten` and `TimesCooked` on composed foods and `UsedInCount` on leaves, with one query per kind (sqlc `FoodHistory`, `UsedInCount`). Plates marked `not_eaten` and draft rows do not count.

`GET /api/foods` filters: `max_minutes`, `not_eaten_weeks`, `created_within_days`, `today`, `sort=name|last_eaten|created` (`last_eaten` ignores favorites). Recipes carry `last_eaten` (`YYYY-MM-DD`), `times_cooked` and `per_portion` (batched `PerPortionDetailedMany`); leaves carry `used_in_count`. Plate feedback statuses are `loved`, `disliked`, `not_eaten`; others are `400 error.feedback.invalid_status`. `GET /api/foods/macros` serves the plate sheet's macro preview. `GET /api/foods/{id}/scaled?portions=` (required, 0 < p <= 100) returns the scaled ingredient list.

## Diet class

Package `domain/diet` (no domain imports): `Class` (`vegan` < `vegetarian` < `pescetarian` < `omnivore`, plus `unknown`), `Order`, `Valid`, `Max` (any unknown child, or none, gives unknown), `Compatible(class, dietType)` (class ≤ type; unknown never) and `Classify(name)`, a 3-stage data-driven en/de keyword classifier: phrases like "Kokosmilch" add their class and are cut out of the name, then markers like "vegan" or the animal keywords run on the rest, and the result is the max of everything found (else a plant keyword → vegan, else unknown); umlauts and ß are folded.

Migration 00035 adds `foods.diet_class`, an override only (NULL = derived, nothing backfilled; D28). `food.Food` carries `DietOverride` (stored) and the derived `DietClass`/`DietClassSource` (`auto` leaf name, `user` override, `derived` recipe max over its children). `food.Service.Derive` sets them (`DeriveDiet`: one `LoadTrees` for all recipes without an override); `food.SetDietClasses(nodes)` does it on an already loaded tree.

- Every food JSON has `diet_class` and `diet_class_source`; scaled ingredients and import draft ingredients carry `diet_class`.
- `GET /api/foods?diet=<class>` keeps foods with class ≤ it, unknown excluded. The class is not stored, so the service filters after the SQL query and pages afterwards.
- `PUT /api/foods/{id}/diet-class {class | null}` sets or clears the override (both kinds); error `error.food.invalid_diet_class`.
- `PUT /api/foods/{id}/no-cook {value: true|false|null, serving_g?: number|null}` (an absent `serving_g` keeps the stored serving, an explicit `null` clears it) sets or clears the "needs no cooking" override (migration 00049 `foods.no_cook`, NULL = derived; both kinds) and the serving size (migration 00052 `foods.serving_g`, REAL > 0, leaf only; an absent or null `serving_g` clears it, so a caller sends the food's whole state; `error.food.invalid_serving`, `error.food.serving_leaf_only`). Every food JSON has `no_cook` (effective), `no_cook_source` (`user` | `derived`) and `serving_g`; see No-cook detection. (Audit PR D kept the stored eat-as-is flag as `no_cook`; there is no separate `eat_as_is` column or endpoint.)

Plate feedback (spec §6.6): loved/disliked move the plate's recipe tags into `likes`/`dislikes` and out of the opposite list; role names and `explore` are skipped.

## Plan generation

Package `domain/planning` turns "plan my week" into a checked draft: context assembled in Go, one proposal from a chooser (LLM or heuristic), the checker, a bounded repair loop, then drafts persisted. The HTTP handlers (`handlers/plan_generate.go`) and the chat agent's `regenerate` tool (D8) call it.

- **Checker.** `planning.Check(State, Target) []Issue` applies the hard rules H1–H9 to a pure `State`; `Merge(State, Target, Proposal)` lays a proposal over the fixed context (proposed plates get negative ids, sessions keep their key); `ComputeScore` and `ToSnapshot` complete the pipeline. Issue codes beyond the spec's: H1 `extra_plate`, `missing_plate`, `cook_in_none_cell` (an uncooked session cooks on a No plate cell; the agent's `move_cook` / `cook_at` refuse such a cell and name up to three valid ones, and H2 `move_cook` options skip them); H6 `confirmed_in_target`, `session_outside_target`; H7 `unknown_food`, `unknown_session`, `not_composed`, `session_food_mismatch`, `duplicate_session_key`, `invalid_portions`, `plate_without_components`, `plate_outside_target`, `plate_on_confirmed_cell`. H8 (variety) judges only the **proposed** (unconfirmed) cooks of a run: confirmed rows and routine cells are never subject to it, and it relaxes to the `variety_relaxed` warning when fewer eligible mains exist than cooks. **On persisted data** (the board, chat dry runs and evaluations, alternatives: `!index.merged`) a cook whose only repeat is another cook or a confirmed plate **inside the plan window** is the warning `variety_repeat_week` (the user's own choice of the week; the S8 count still limits how often a dish appears); a repeat from before the window (`LastEaten` or a cook before it) stays the `variety_repeat` violation, and a planner run's merged state keeps the violation for both (so the repair loop never sees `variety_repeat_week`: merged states only). The earliest earlier cook decides (`earlierCook`), so a pre-window cook wins over an in-window one. **Data limit:** `LastEaten` is the newest confirmed plate, so an older pre-window eating hidden behind a confirmed in-window plate reads as a week repeat. `GET /api/plan` runs the same `Check` and filters to H1, H2, H5 and H8.
- **Scopes (D6).** `window` (generate), `day`, `plate`, `side` and `empty_cells`; `Scope.From`/`To` bound `empty_cells` (the re-plan). Everything outside the scope and everything confirmed is fixed context. Use the name `empty_cells`: the frontend legacy gate bans `fill_empty`/`replace_all`.
- **Day scope stays inside the day (slice 3b).** The target is the day's cells (from today on); the rows it replaces are the day's **draft plates only** (`scope_json.plate_ids`, no session ids), removed through `plate.Service.RemoveMeals` (`Service.removeDay`; a plate gone or confirmed since resolve is `ErrStateMismatch` → `error.plan.changed_during_run`). The save compares its removal (`Removed` and `AlsoChanged`) with the dry run's; a difference (another plate of an affected batch changed meanwhile) fails the save with `ErrPlanChanged`, nothing written, so a batch cooked on the day keeps its later meals (the cook re-anchors to the earliest, R1) and a leftover of an earlier batch shrinks it (D11). A re-anchored cook that would give its new day more cooking times than allowed goes back to its cell on the replanned day (`keepCooks`, B-3: the replanned day adds no hard issue; `MoveCook` through the `PlateService` port), and a move that still leaves such an H2 makes the run save nothing (`movedCookH2`, `error.plan.hard_rule_open`). Confirmed plates on the day stay. The chooser plans on the plan as it will be: `generate` runs the removal and `Builder.Build` in a unit of work that is rolled back (`Service.dryRun`, never nested in another `InTx`), and the save repeats the removal for real, so a failed run writes nothing. The save's moves are recorded as `scope_json.also_changed` (the meal operations' `AlsoChanged`) and a run note per move ("Lasagne now cooked Thursday lunch", `textCookMoved`).
- **Preview (`planning/daypreview.go`).** `GET /api/plan/regenerate/preview?scope=day&date&start[&today]` returns `{replaced: [plate ids], also_changed: [AlsoChanged], confirmed_affected: [plate ids of confirmed meals that became their batch's cooking meal]}`; it runs the run's own removal in a rolled-back unit of work (`dryRun`), so the preview is what the save does. Errors: `scope` other than `day` or a missing/bad `date` is `400 error.plan.invalid_scope`, a date outside the window or before today too, `start` not a shopping day `400 error.plan.invalid_start`. The sheet asks only when `also_changed` is non-empty.
- **Undo of a regenerate.** The save (removal, `Apply`, light store) is one `plate.Service.Recorded` unit of work; for the `day` and `plate` scopes its event range is stored as `scope_json.undo` (the finish rewrites `scope_json`: `RunEnd.ScopeJSON`, `FinishAIRun` `scope_json = COALESCE(?, scope_json)`) and `GET /api/plan/runs/{id}` returns it as `undo` (`{first_event_id, last_event_id, cells: []}`) once the run is `ok` or `partial`; omitted otherwise. `POST /api/plan/revert` takes it back through `RevertChecked` (generator-actor events revert like any; a later edit of a run row is `409 error.plan.change_stale`). **Limit:** the undo restores plate events only; the `plan_light` rows the same save wrote (`Light.Replace`) are not restored, so a light request the run stored stays after Undo. (The chat `apply_changes` Undo does restore them, see Plate audit trail.)
- **Plate scope: a different dish.** `resolve` `ScopePlate` puts the replaced plate's composed foods into `ChooseInput.Exclude` (besides `avoidBatches` for a leftover plate). The heuristic never cooks them at the target cell (`mainCandidate`) and never grows their batch; it eats the old batch only as the `eatAnyway` last resort (a maxed cooking day, else H1). The LLM chooser drops them from its candidates (`plan.context` `excluded` reason `replaced_by_target`). Pinned by `TestService_RegenerateScopes`. **D3 (audit PR D):** this exclusion (and `avoid`) applies to the plate and day scopes only; a window generate or regenerate excludes nothing (`TestRunLog_WindowGenerateExcludesNothing`) and the variety rules (S8, variety weeks) handle repeats.
- **Alternatives (`planning/alternatives.go`).** `Alternatives(State, Target, AltRequest) (AltResult, error)`, pure: for one draft plate in the window (`ErrNotFound`; confirmed: `ErrInvalidInput`) and `what` = `meal` (replace the main, remove every other component), `main`, `side` (the given `ComponentID` or the only non-main component, else `ErrInvalidInput`) or `add`. Candidates are the state's foods that fit the position (main: a recipe whose role counts as main for the slot kind; side: side roles, a leaf's by `FoodFacts.LeafRole`, its effective role; add: side, dessert, drink or no-cook) and the constraints (`max_minutes` on a fresh cook, unknown minutes fail it; `diet` on top of a restricted household diet, an omnivore household takes unknown classes as H5 does; `roles`; `search` over name and `FoodFacts.Tags` as `find_foods`; `tags`; `min_protein_g`, `max_kcal` of the new component; `no_cook`); every food already on the plate is excluded. A recipe is tried fresh, as `cook_at` and once per persisted batch of it that cooks on or before the cell within keep days (`session` source: a batch with a surplus that holds the plate, or one that exactly covers its meals, which grows with the plate as D11 does; one short of its meals is skipped); a leaf is `leaf`. **`cook_at`** (`cookAtCell`, only when the plate's own cell does not cook): the recipe cooks fresh on the latest cell that already cooks on or before the plate's cell (same day or an earlier one), else on the latest plan cell of an earlier day with a free occasion that does not hold only confirmed plates (a cell without plates is fine); always in the window, not before today, within the recipe's keep days of the plate, never a routine or `none` cell; evaluated as a new session there, so the plate's day gets no new occasion. Without it a leftover meal on a day at `plan.max_cook_occasions_per_day` had an empty list: every fresh candidate was an H2 (measured on `single_batch_cooker`: 189 of 189 drops on leftover plates were H2, 7 main lists empty; now 0). Each is applied to a copy (portions or grams of the replaced component, else 1 portion / `TypicalLeafGrams`) and `Evaluate`d; a new hard issue (H2 cap, H3 batch overdrawn, H8, ...) drops it. Ranked by fewest new soft issues, no new cooking occasion, source (session, then cook_at, then fresh or leaf), the food's S8 dish count after the change, no second side of the same role, kcal fit (a light meal's kcal over its cap, a hearty meal's under its minimum, a light or hearty day's distance to its even share; 0 otherwise), oldest `last_eaten` (never first), food id (a fresh or `cook_at` recipe that already has a cook in the window ranks after the S8 count, `altRank.weekCook`: a `variety_repeat_week` warning drops nothing); a recipe passing both fresh and cook_at is listed once, by the better rank. Result (default 5, max 10) `{current?, alternatives, hint?, empty_reason?}` (`current`: the replaced component with its role, kcal and the light cap/minimum; `hint`: a `meal` swap drops the plate's other components; `AltRequest.Light` `lighter|heartier` evaluates the plate as a light/hearty meal and keeps only candidates meeting the cap/minimum; a food is listed once by its best source; side replacements rank a composed side of the same role first and offer leaves only when no-cook), each alternative: `food_id`, `name`, `source` (`fresh|session|cook_at|leaf`), `session_id`, `cook_at` (`{date, slot_id}`), `total_minutes` (fresh and cook_at), `role`, `food_kcal`/`food_protein_g` (the new component alone), `plate_kcal`/`plate_protein_g` (the plate after the change, per eater; the HTTP body and the frontend use the same names), `day_kcal`, `day_pct`, `week_pct`, `cook_occasions_day`, `new_issues` (soft, without options) and `ops`, the `apply_changes` ops in order: `swap` (`plate_component_id`, `food_id`, quantity) for a fresh or leaf replacement, `replace` (`plate_id`, `plate_component_id`, `food_id`, `cook_at`, quantity; for `add`: `add` with `cook_at`) for a cook_at source, which `POST /api/plates/{id}/replace` takes too, `replace` with `session_id` (`plate_id`, `plate_component_id`, `food_id`, quantity; keeps the position, the board applies it as one replace) for a session source (`add` with `session_id` when nothing is replaced), and `remove` per dropped component (`OptionOp.SessionID`, `OptionOp.CookAt`). **`empty_reason`** (`EmptyReason`, only when the list is empty): `{candidates, dropped?, why?}` (`why`: the blocking rule in words with numbers), the candidates that fit position and constraints (0: loosen a constraint), counted per candidate not per food: a recipe tried fresh, as `cook_at` and per batch is several (`dropped` counts the same units) and per `rule.code` how many each first new hard issue dropped; a candidate whose incomplete nutrition data would make its plate or day `nutrition_missing` (it was not before) is dropped as `nutrition_missing`; the board and the agent say why instead of "nothing fits". Not simulated: the R1 re-anchor of the replaced batch (replacing a cooking main whose batch feeds later meals moves that cook at apply time; an H2 there is not foreseen). `planning.Service.Alternatives` builds the window with `Builder.Build` in one `InTx` (start must be a shopping day) over `WindowTarget`. **`POST /api/plan/alternatives?start&today`** body `{plate_id, what, plate_component_id?, constraints?: {max_minutes, diet, roles, search, tags, min_protein_g, max_kcal, no_cook}, limit?}` returns `200 {alternatives: [...], empty_reason?}`; writes nothing.
- **Endpoints.** `POST /api/plan/generate {start, chooser?, instruction?, eaters_by_date?, include_new_recipe?}` and `POST /api/plan/regenerate {scope, start, chooser?, instruction?}` return `202 {run_id}` (`?today=` is the client's date). `GET /api/plan/runs/{id}` returns status, `stage`, counts, issues, score and window; the client polls it, there is no SSE (D9). Regenerate keeps each day's eaters (guests) and never asks for a new recipe. Fewer than `setup.RecipeTarget` composed recipes is `error.plan.not_enough_recipes`; a second run on a window is `error.plan.generation_running`. `POST /api/plan/accept` and `/discard` `{from, to}` act on the window's draft closure (accept returns `{plate_ids, session_ids}`, the body of `POST /api/plan/unaccept`; discard returns `{removed}`, which `POST /api/plan/restore` brings back as drafts); `POST /api/plates/{id}/confirm|unlock` and `/api/cook-sessions/{id}/confirm|unlock` move one row's closure. Confirmed wins wherever a link joins different states.
- **Runner.** A generation is asynchronous: `start` validates, picks the chooser, reserves the window in `planning.Progress` (the in-memory registry; one run per window), creates the `ai_runs` row and runs in a goroutine on a **detached ctx** with a 3 minute timeout (`runTimeout`). A panic ends the run as an error instead of the process. Stages (D35): `resolving`, `choosing`, `checking`, `repairing`, `saving`. `Progress.Running(start)` feeds `running_run_id` on `GET /api/plan`, which is how a reloaded board re-attaches. `Service.Wait` lets shutdown wait for running runs; `Service.Await(ctx, id)` blocks until one run finished (a per-run done channel in `Progress`, closed after the row is finished) and returns ctx's error when ctx ends first; `Deps.Go` lets tests run synchronously. At startup `FailInterruptedRuns` ends `running` rows left by a crash as errors (logs `ai.run.interrupted`). A run with no open `plan` cell skips the chooser (routines are still applied; it ends `ok`, cost null).
- **Chooser selection.** `Deps.Choosers` maps `airun.ChooserLLM` / `ChooserHeuristic`. A request **without `chooser`** uses the LLM only when a provider resolves (the chooser's `Ready`), else the heuristic. Explicit `llm` without a provider is `503 error.ai.provider_missing`; a provider that cannot be built is `502 error.ai.provider_error`; a reply that never yields a readable plan ends the run `error.ai.invalid_plan`. The e2e backend always has the fake provider, so heuristic e2e requests must pin `chooser: heuristic`.
- **Heuristic** (`heuristic.go`, run-log version = `planning.HeuristicVersion`, currently `h19`): deterministic, no AI. The first day cooks at its earliest cell; later days cook at dinner and the earlier cells eat leftovers (sessions grow within keep days). Leftover plates (a batch's cover and later cells eating a session) respect `meat_days_per_week_max` (h6); only a cell nothing else can fill takes a meat leftover. Bump the version when it changes what it picks. A lunch or dinner (slot kind `meal`) is cooked only with a recipe of role main: with none available the cell stays empty (a run note, H1 reports it), and a leftover that has to exceed `meat_days_per_week_max` to fill a cell is allowed only with a run note (h7); a cell left empty by the day's cooking cap makes the heuristic rerun with a cook forced on the latest earlier cell whose leftovers reach it (h8: batch-closure cells of a regenerate are refilled). h9/h12: `topUpFloors` (`heuristic_floor.go`) lifts every complete day in order: (1) under its H9 floor up to it (portions of proposed mains and carb sides, and their sessions so H3 holds, round up; then verified no-cook foods, S2's `candidates` + `verify`); (2) `closeProteinGaps` when a g/kg target is active; (3) under its S2 band low end up to it, while the week stays under its target; (4) while the week average is under its target, the days furthest under go up toward it by at most what the week still lacks (portions round down). Growth is at most 1.5x of the planned portions over all passes (`topUpBase`), light meals never grow, a food is not added twice a day. h13: `pickMain` tie-breaks on the DGE food rules (see DGE weekly food rules): a fish or legume main while the week has none, and a meat main that would take the estimated week past 300 g comes later; they rank after likes and a 1 kcal fit bucket (`dgeFitBucket`: wider buckets regressed `replan_one_day`), before the exact kcal fit, so kcal and protein behaviour holds (eval: all scenarios unchanged). h14: the S8 cap (`plan.max_dish_meals_per_week`) is soft for the heuristic: `cover` stops a batch's growth at the cap, `growable` skips capped dishes and `pickMain` ranks a capped dish last instead of skipping it; the last-resort `eatAnyway` may pass the cap, and existing batch portions are always eaten (`pickSupply` is not capped), so the cap never leaves a cell empty (H1). Measured on `replan_one_day`: plates written 8 to 7 with all 14 lunch/dinner cells filled (coverage 1); the Tuesday batch now stops at 3 meals and Thursday dinner keeps the generate run's plate. h14 also honours hearty cells and the plate-scope `Exclude`. **No-cook adds are capped per day over all passes** (`dayAdds`): at most 2 plain fillers plus 1 protein add, each at most 200 g and 20 % of the day target, on different plates (lunch and dinner) before any plate takes a second; past the cap the day stays short and `kcalNote` says so (this can leave a day under the floor as an H9 when the library has little no-cook food). A filler is the food that fits the kcal gap best; sweets are never fillers (`FoodFacts.Sweet`, `planning.IsSweet`: a leaf with at least 20 g sugar and under 5 g fibre per 100 g, the library has no food category; WHO free sugars under 10 % of energy). ### Mid-week re-plan

`GET /api/plan/replan/preview?from&to[&none=date:slot…][&today]` returns `{none_cells, confirmed_affected, spare}`: the No-plate cells that hold plates, the confirmed plates a re-plan would remove, and the batches that would cook more than is still eaten (`spare[]` with `portions`, `freezable`, `mutable`; a batch is mutable only when it is not cooked and cooks on or after `from`, and only a mutable one can be reduced; `freezable` also holds for cooked ones, while `plan.freezer_keep_days` from their cook date have not run out at `from`).

`POST /api/plan/replan {from, to, none_cells, unlock_confirmed, spare: freeze|keep, regenerate, chooser?, instruction?}` returns `{removed, run_id, unassigned}`. A cooked or earlier batch's freed portions are frozen when freezing is on and the recipe freezable (portions stay, frozen grow); portions that end up eaten by no plate are `unassigned` (preview `spare[].unassigned` counts them for a freezing re-plan). **`none_cells` is part of the contract**: the re-plan writes the No-plate overrides itself in the same transaction, because the availability API refuses `none` on an occupied cell. Confirmed plates need `unlock_confirmed`, else `409 error.plan.confirmed_affected` lists them; `from` before `?today=` is `400 error.plan.replan_past`. Days before `from` and cooked portions are never touched. The server's only sources of "today" are `?today=` and its clock. The window is reserved from before the removal until the run starts, so no other generation slips in between; if the run fails to start after the commit, the error is logged and `run_id` is null. The overrides go through `availability.SetOverride` (`RemoveMealsAt`), so a cooked-ahead batch whose empty cook cell becomes `none` re-anchors to its earliest meal (R1; decision, `TestReplan_NoneCookCellReanchorsACookedAheadBatch`). `removed` alone cannot undo a re-plan (the overrides and the new run are not in it), so a re-plan has **no Undo**.

`plate.Service.RemovePlates(ctx, ids, keep)` is the removal primitive: one unit of work; each session in `keep` ends with exactly its (frozen) portions and survives without links, so a cooked batch is never deleted; other sessions follow D11. An uncooked session that loses the plate on its cook cell but keeps other links **moves its cook to the earliest remaining plate** in the same transaction (a session update event; this can add an H2 on the new day, accepted). A missing plate is `ErrNotFound` and nothing is removed.

### Offline eval

`internal/eval` and `cmd/plantry-eval` run plan generation offline (spec §8.4): an embedded 30-recipe library (`library.json`; an ingredient may carry a `no_cook` override and a `serving_g` where the derived eat-as-is guess is wrong) and twenty-three scenarios (`internal/eval/scenarios/*.json`), each run on a fresh in-process database copied from a migrated template, through services wired like `main.go`. A scenario's expectations: `evaluation` (asserts on the saved plan's closing `plan.evaluation`: `week_pct`, `week_protein_pct_min`, `min_day_share`, `light_adjusted`, `issues_present`/`issues_absent`, `notes_contain`; the nutrition scenarios `nutrition_maintain` (2000 kcal), `nutrition_maintain_1800`, `nutrition_maintain_2500`, `nutrition_lose`, `light_meal_weekday_dinners`, `light_dinners_no_addons` (no S9, no add-on on a light meal), `addon_caps` (a low-kcal library: adds at serving size, no S9, no H9; the week may stay under its band, at least 90 %), `hearty_meal`, `light_two_meals_floor` (the floor stops two light meals: an honest H9), `light_day`, `protein_gap_week`, `unreachable_floor`; a step takes `light`, the profile `goal`/`weight_kg`/`sex`), `allow_violations`, `min_plates`, `no_plate`, `max_dish_meals` (always on, every scenario: no main in more meals than the scenario's `plan.max_dish_meals_per_week`, default 3; `away_thu_fri` sets 5, the smallest cap that keeps its frozen batch spanning Thu and Fri), `kept_confirmed`, `unchanged_before`, `unchanged_outside` (a day regenerate: no plate dated on another day changes, plus `day_batch_kept`: every later meal that ate a batch cooked on the day before the step still eats it; applies only when the chooser made such a batch, else it passes with detail "not applicable" in the report; `replan_one_day`), `frozen_spare`, `min_repeats`, `alternatives` (after the measured step every draft lunch or dinner main from today on gets at least one alternative; `single_batch_cooker`, `replan_one_day`). The plate service's clock is the running step's `today` (`env.today`), so the R1 re-anchor works on the scenario's dates.

```bash
go run ./cmd/plantry-eval                                   # all scenarios, heuristic chooser, 3 runs each
go run ./cmd/plantry-eval -scenarios family_daily,away_thu_fri -runs 5
go run ./cmd/plantry-eval -chooser llm -prompt-version p7   # scripted LLM mode, no network
PLANTRY_EVAL_LIVE=1 PLANTRY_AI_PROVIDER=anthropic PLANTRY_AI_API_KEY=... \
  go run ./cmd/plantry-eval -chooser llm -model <model>     # live: real provider, costs money
go run ./cmd/plantry-eval -compare earlier.jsonl            # per-component diff against an earlier report
```

Flags: `-scenarios` (comma-separated, default all), `-chooser` (`heuristic` or `llm`), `-runs` (default 3), `-model`, `-prompt-version`, `-out` (JSONL, default `plantry-eval.jsonl`, gitignored), `-compare`, `-keep-db <dir>` (keeps each run's database as `<scenario>-<run>.db` with its run steps for audit; default: removed; a live run (`PLANTRY_EVAL_LIVE=1`) always keeps them: without `-keep-db` they go to `plantry-eval-dbs/<timestamp>/` (gitignored) and the path is printed). Scripted LLM mode feeds the heuristic's proposal through the real `LLMChooser` and its `prompt_dates` check. Live mode needs `PLANTRY_EVAL_LIVE=1`, `PLANTRY_AI_PROVIDER` (`anthropic` or `openai`), `PLANTRY_AI_API_KEY` and a model (`-model` or `PLANTRY_AI_MODEL`). The command prints a summary, writes one JSONL record per run and exits non-zero when a run failed an expectation (the report is still written). `cmd/plantry-eval/testdata/compare.golden` is rewritten with `UPDATE_GOLDEN=1 go test ./cmd/plantry-eval/...`. Re-run the suite after changing the heuristic, the checker or a prompt, and `-compare` against the previous report.

## Shopping list

Package `domain/shopping`; `GET /api/shopping-list` returns sections in walk order. Rules:

- Confirmed rows only; `include_drafts=true` adds draft sessions and draft leaf plates, and `has_drafts` reports whether the range has any either way.
- It buys the cook sessions' `portions` (not what plates consume) plus leaf components (amount × eaters), for the range's dates. The default range is `ShoppingDefault` of the anchored window; `from`/`to` override it inside the window containing `from`.
- Amounts sum in metric base units (`units.ToBase`); `display` is in the contributions' unit when they share one, otherwise grams; `buy` is set for count units only.
- `used_in` lists the sessions or leaves an item is bought for, in cell order; `draft` marks a use from a draft session or draft plate (only with `include_drafts`).
- Sections are the `food.ShopSections` enum (`domain/food/shop_section.go`). A food's `shop_section` column (migration 00031) overrides `shopping.Classify`, a 3-stage data-driven classifier (packaging, phrases, head noun). `PUT /api/foods/{id}/shop-section` sets it for leaves only; errors `error.food.invalid_shop_section`, `error.food.shop_section_leaf_only`.
- `food.LoadTrees` loads recipe trees in one query per level.

## Plate audit trail

Go migration `00030_plate_events.go` (sqlc reads `schema_patches/00030_plate_events.sql`), `domain/plate/events.go`, repo `adapters/sqlite/plate_event_repo.go` (D20). 00030 also rebuilt `plates` and `cook_sessions` with `AUTOINCREMENT`, so an id never names two rows over time.

The fake records requests so tests can assert the research prompt and the replayed blocks. `chat-scripts/discovery.json` is the template for discovery runs (see Discovery).

## Programmatic tool calling

Anthropic only (docs: `agents-and-tools/tool-use/programmatic-tool-calling`): the model writes Python in Anthropic's code execution container that calls our tools, so fan-out and "try several drafts, keep the best" cost one model turn.

- **Request.** `llm.Request.CodeExecution` (opt-in) and `Container`; `llm.Tool.AllowedCallers` (`llm.CallerDirect`, `llm.CallerCodeExecution` = `code_execution_20260120`). The Anthropic adapter sends `{"type":"code_execution_20260120","name":"code_execution"}` first in `tools`, `allowed_callers` on the tools that list it and `container` only when `plan` says the model may: `capabilities.code_execution.supported` from the Models API (the top-level capability, not `server_tools.code_execution`; Haiku 4.5 accepts the tool but not this), no forced `tool_choice`, no earlier rejection. Otherwise it sends none of it and records why in `sent.fallbacks` (`code_execution_unsupported_by_model`, `code_execution_with_tool_choice`, `no_code_callable_tools`, `capability_unknown`, `capability_lookup_failed: …`, `code_execution_rejected_by_model`). A 400 naming `code_execution`, `allowed_callers` or `programmatic` is retried once without (attempt reason `code_execution_rejected_400`) and remembered per model; the retry strips the code blocks from the replayed history. **A request that does not send the code tool (setting off, capability gone, rejected) replays the history without code blocks** (`llm.StripCodeBlocks`: `server_tool_use` of code execution, its result blocks, the code-called `tool_use` and their `tool_result`; recorded as fallback `code_blocks_stripped`): the docs do not say whether the tool definition is needed to replay them, and a history without them is always valid. Web search blocks are not touched. A 400 naming the container while no programmatic call is pending (an expired container) is retried once without `container` (`container_rejected_400`, fallback `container_dropped_after_400`); with a call pending the continuation requires it, so that 400 is the caller's. **`anthropic-version` stays `2023-06-01`**: the 2026-10-21 version changes sampling parameters, assistant documents and deprecated fields; programmatic tool calling is not version-gated (decision from the docs; not verified live). The 400 fallback above is the safety net and its error body is stored on the failed step.
- **Response.** `llm.Response.ContainerID` / `ContainerExpiresAt` (message_start and message_delta `container`); `ContentBlock.Caller` on a `tool_use` (`{type: direct}` or `{type: code_execution_20260120, tool_id}`, replayed on later requests). `server_tool_use` and `code_execution_tool_result` blocks replay as `server` blocks. A reply that pauses on code-called tools has `stop_reason: tool_use`; the continuation must carry `container` and answer with a user message holding only `tool_result` blocks (the loops already answer every call with results only). `pause_turn` with no tool call makes the chat loop and the planner chooser resend the paused turn as it is (no repair used).
- **Loops.** The chat loop (`RunRequest.CodeExecution`, `Container`, `SaveContainer`) keeps the container for the turn and stores it per conversation (`ai_conversations.container_id` / `container_expires_at`, migration 00044), reused by the next turn while `container_expires_at` is in the future (the expiry is refreshed from every reply; an expired one is logged as `agent.container.expired` and the turn starts without it). The **chat agent has it off** (D4, `chatProgrammatic = false` in `agent/service.go`): no code execution tool and no `allowed_callers` for chat whatever `ai.programmatic_tools` says (in the paid runs scripted chat calls cost more than they saved); the loop plumbing stays for the const. The planner keeps it. Every tool call runs with `llm.WithCaller(ctx, caller)`; `ToolSet.Execute` refuses a code call of a tool that is not `CodeCallable` (`ErrCodeCallRefused`; `allowed_callers` is guidance, not a boundary). Code-callable: `find_foods`, `get_plan`, `find_alternatives`, `apply_changes`; **`apply_changes` from code must set `dry_run: true`**, otherwise `ErrCodeCallRefused`, so writes stay direct and the final change set is one visible decision. The planner chooser (`LLMChooser.WithProgrammatic`) offers `evaluate_plan` to code (`maxCodeEvaluations` = 30 per run, direct ones keep `maxEvaluations`) and keeps the run's container; `submit_plan` is direct only: a code-called `submit_plan` is answered with an error and never counts as the submission.
- **Bounds.** A script that awaits one tool call at a time is one request per call, so requests that only continue code (the reply's tool calls all come from code, or a `pause_turn` resend) are not model turns. Model turns keep their caps (planner `maxModelCalls`, chat `MaxIterations`); code continuations have their own (planner `maxCodeEvaluations`, chat `MaxCodeContinuations` = 40), and a hard total per run (planner `maxRequests`, chat `MaxRequests`). Planner: at a bound the run ends with the last submitted proposal and a run note, or `error.ai.invalid_plan`, and logs `plan.run.stopped`. Chat: at `MaxCodeContinuations` the pending code-called calls are answered with an error ("stop calling tools") so the model closes the turn with a message (log `agent.loop.code_limit`); at `MaxRequests` or `MaxIterations` the turn fails with `error.ai.iterations_exceeded`.
- **Output cut-off.** A reply with `stop_reason` `max_tokens` never executes its tool calls (their input may be cut; an empty `evaluate_plan` once evaluated an empty plan). Each `tool_use` is answered with an `is_error` tool result saying the reply was cut off, nothing was run, and to keep reasoning short and let the tools compute (planner: put the draft into `evaluate_plan`; chat: `apply_changes` with `dry_run`). It is a model turn under the existing bounds (`maxModelCalls`, `MaxIterations`), not a repair or attempt; a cut reply that only holds code-called tool calls counts as a model turn too (bounded: chat 20 x 16000 tokens, planner 14 x 32000). A cut tool input arrives as a JSON string of the partial text: it is replayed as `{}` (`llm.ObjectInput`; both adapters and the stored chat history), while the `is_error` tool step keeps the raw text in `args_json` and the `llm_call` step's `response_json` keeps it as received. Recorded as `is_error` tool steps (result `{"error": ...}`), a run note in the planner (once) and the log lines `plan.run.cutoff` / `agent.loop.cutoff` with `model_seq` (the cut reply's step) and `tool_seqs` (every answered call's step). A text-only reply cut at `max_tokens` still ends a chat turn as a normal final answer.
- **Stored conversation.** The chat loop buffers the messages of an open code turn (`llm.CodeTurnOpen`: a code server block without its result block) and stores them once the turn closes. If the turn ends first (failure, cancel, cap), the stored remainder omits the code blocks, the code-called tool calls and their results (`llm.StripCodeBlocks`), so the next request never continues from unanswered programmatic calls (a text message there is a 400). Earlier messages are never rewritten.
- **Logging.** See AI run log: `code_execution` steps, `caller` columns, `ai_runs.container_id`, `request_json.sent`.

## Prompt caching (Anthropic)

`encodeRequest` puts a 5 minute `cache_control` breakpoint on the system prompt and on the last tool, and, only when `llm.Request.CacheTail` is set (the chat agent loop and the planner's LLM chooser, which resend their history; one-shot calls (importer, lookups, discovery) would pay the 1.25x write and never read it), on the last block of the last message (3 of the 4 allowed), so a request resends its history as a cache read instead of fresh input; before, only system and tools were cached and every large tool result (`evaluate_plan`, `apply_changes`, `get_plan`) was billed as uncached input on every later turn. Each breakpoint reads back from an earlier request's write, and the 20-block lookback is not a problem here because a turn adds one assistant message and one user message (parallel tool calls collapse to one position). A server block (verbatim thinking, code execution, web search) cannot carry the marker, and neither can a `tool_result` answering a code-called `tool_use` (`codeCalledIDs`; the API answers 400 and the fallback used to turn programmatic calling off, audit B5; `TestStream_TailBreakpointSkipsCodeCalledResults`), so the breakpoint goes on the last other block of that message, and no tail marker when none is cacheable (`tailIndex(content, codeCalled)` picks the block, `tailCacheable` reports it, and decides what `llm.Effective.CacheBreakpoints` reports: `system`, `tools`, `messages`). Check the effect with `usage.cache_read_input_tokens` of the run steps.

Bump `HeuristicVersion` when a reason code's meaning changes.
- **Programmatic tool calling (00044).** `ai_run_steps.type` also allows `code_execution`, recorded by the metered client for every code execution result in a reply (`airun/codeexec.go`): `name` is the server tool (`code_execution`), `args_json` the code, `result_json` `{tool_use_id, container_id, result_type, stdout, stderr, return_code, error_code}` (capped like every tool result, 256 KiB), `is_error` for a non-zero return code, an error result or `TimeoutError` in stderr (a pending-call timeout), `status` (`pending` when the code was issued, `completed`, or `unfinished` when the run ended first; the step is written when the code is issued and updated when its result arrives or the run finishes), `code_execution_requests` (the reply's `usage.server_tool_use.code_execution_requests`, `llm.Usage.CodeExecutionRequests`), `duration_ms` from the reply that carried the code to the end of the reply that carried its result (so it includes the pauses for tool results). A `tool_call` step (and the planner's `plan.evaluation` steps) made on a tool call carries `caller` (`direct` | `code_execution`) and `caller_tool_id` (the code's server tool use id; NULL for steps the code writes itself). A code-called tool's result is not part of the model's context (the API keeps it inside the code), so that step's `result_json` is its only copy. `ai_runs.container_id` is the run's last container; `request_json.sent` adds `code_execution` (on/off), `code_tools` (tools sent with a code caller) and `container` (id sent); `response_json.container_id` the reply's. `ai.tool.call` carries `caller`, `caller_tool_id`, `container_id`; `ai.llm.call` carries `container_id`, `sent_code_execution`, `sent_code_tools`; `ai.code.execution` logs each code step (return code, byte counts). The run detail API shows `container_id`, and per step `caller` and `caller_tool_id`.
- **`ai_prompts`** — system prompt text stored once per distinct hash. Every distinct system prompt of a run is stored (a lookup has two: translate and pick-best); `ai_runs.prompt_hash` is the first call's.
- **`ai_tool_schemas`** — tool definitions (`json`, a `[]llm.Tool`) stored once per distinct hash.
- **Replay.** Call *i*'s request is call *i−1*'s messages cut to `message_offset` plus call *i*'s `messages`, the prompt by `system_hash`, the tools by `tools_hash`, `temperature`, `max_tokens` and the step's `name` as model. Callers append the assistant reply to their history themselves, so replies are already in the next delta; never insert `response_json` into a reconstruction. `domain/airun/replay_test.go` (`reconstruct`) is the reference.
- **Retention.** At startup and after a finished run (at most once per hour; both in a goroutine, deleting in batches of 500; `Recorder.Wait` waits for them and stops new ones from starting) the steps of runs started more than `ai.run_retention_days` days ago (setting, default 180) are deleted. `ai_runs`, `ai_prompts` and `ai_tool_schemas` rows stay. There is no background scheduler; prune failures are logged at warn and not retried for an hour.
- **Cost is not stored.** `airun.Cost(model, provider, tokens, overrides)` (`cost.go`) computes it on read: an `ai.price_overrides` entry for the exact model id wins, else the built-in table entry with the longest model-id prefix (`PricesAsOf`, sources cited next to the table). Missing cache prices default to 0.1× / 1.25× of the input price (0.5× / 0 for OpenAI, whose input count includes the cached tokens, which are subtracted). An unpriced model is `nil` ("cost unknown"); a run without tokens costs 0. slog lines all carry `run_id`, `request_id` and (chat) `conversation_id` (`Run.LogAttrs`): `ai.run.start` / `ai.run.end` (with duration, reasoning, `error_key`), `ai.llm.call` per model call (step seq, provider, requested and served model, duration, ttft, all token kinds, stop reason, tool choice, effective max_tokens, request/response bytes; on failure the provider status and error type, never the key or text; WARN), `ai.tool.call` per tool call (tool, duration, `is_error`, `error_key`, `args` reduced to numbers, dates, ids and the short `search`/`kind`/`role`/`diet`/`sort` filter values), `ai.llm.body` at debug (bodies cut to 2000 chars), `plan.run.stage` per generation stage (heuristic runs too: `stage`, `elapsed_ms`, checker counts `by_rule`/`by_code`, saved `plates`, `routine_plates` and `proposal_sessions` (the chooser's; the run API's `counts.sessions` are the persisted ones, routine plates' included), a final `done` line with status and score), `plan.run.attempt` per LLM chooser attempt (on the service logger: counts, `violation_list` as `rule.code@date/slotN plate= session= {params}` capped at 20, or `parse_error` of an unreadable reply; each attempt is also a `plan.attempt` tool step of the run with the same record), `discovery.run.stage` per discovery stage, `import.stage` per import stage (`fetch`, `parse_jsonld`, `fallback` with `step`/`attempt`/`outcome`/`parse_error`/`retry_reason`, `resolve`; the fallback lines carry the run's ids), `anthropic.request.retry` (a retried 400 with its reason and request id), `settings.models.failed` (a failed key check: provider, status, error type, request id; never the key or body), `ratelimit.rejected` (the app's own limiter: path, client, limit). `ai.llm.call` also carries `sent_tool_choice`, `sent_web_search`, `sent_temperature`, `fallbacks`, and on failure `provider_message` (cut to 300), `provider_request_id`, `provider_rate_limit` (`retry-after`/`ratelimit` headers), `after_first_token`, `partial`, `retry_reason`. The debug line `ai.llm.body` may contain prompt and reply text; nothing at info or above does. There is no retry layer for 429/529: they end the call and are logged with their headers. `started_at` of a step is `2006-01-02 15:04:05.000`, unlike `timeLayout` elsewhere (the run detail re-formats it as RFC3339 with ms). `thinking_chars` counts runes of thinking text only (redacted thinking is 0).
- **Read API** (`handlers/ai_runs.go`, `airun.Insights`, repo `ai_run_insights_repo.go`; one query per aggregate):
  - `GET /api/ai/runs?kind&from&to&cursor&limit` (50, max 200) — newest first, `next_cursor` is the last id of the page; items carry `tokens`, `cost_estimate_usd`, `score`, `outcome`, `correction_rate`, `edits`.
  - `GET /api/ai/runs/{id}` — `duration_ms`, `tokens.reasoning`, per step `started_at`, `ttft_ms`, `tokens.{cache_read,cache_write,reasoning}`, `thinking_chars`, `served_model`, `provider_request_id`; plus `app_version`, `scope`, `instruction`, `notes`, `violations`, `error_key`, `prompt_text` and `steps` in seq order; a step's `args`/`result` are text: a tool step's come whole (only the 256 KiB store cap applies, so a cut one is not valid JSON and sets `*_truncated`), an llm_call's are its request/response JSON cut to 8192 characters (`*_truncated`).
  - `GET /api/ai/insights?from&to&bucket=week` (default: the last 12 weeks) — Monday weeks with `runs`, `accepted` (incl. partially), `discarded`, `correction_rate`, `cost_usd` (priced runs), `cost_per_accepted`, `unpriced_runs`; `by_version` groups by kind, prompt version and model with `tokens`, `edits` (chat groups only), `score_avg` (numeric leaves of `score_json`, dotted keys, without per-date entries such as `cook_occasions.per_day.<date>`) and violation counts by rule.
  - `GET /api/ai/prices?model=` (default: the configured model) — `{model, price|null, source: builtin|override|none, as_of}`.
  - Correction rate (D24, sqlc `AIRunCorrections`): plates a run's `generator` or `agent` `create` events made, and how many of them got a `user` `update`/`delete`, or an `agent` one from another run, before the plate's first `accept`/`confirm` event.
  - Edits (sqlc `AIRunEdits`): the distinct plates and sessions an agent run wrote events for; a session edit counts once as its session (its linked plates' events carry `cook_session_id`). Null for a run without agent events.
  - Outcomes: accept, discard, unaccept and restore also move the agent runs that wrote an event for the closure's rows (`RunOutcomes.AgentRuns`), so a chat that only edited a generated draft follows it.
- **Tool choice.** `llm.Request.ToolChoice` forces a tool: Anthropic sends `tool_choice: {type: tool, name}`, OpenAI `{type: function, function: {name}}`; both send `temperature` only when it is > 0. The metered client stores it as `tool_choice` in `request_json`. The fake client's script already replays scripted `tool_use` turns.
- **LLM chooser** (`planning/llmchooser.go`, prompt `planning/prompt.go`, D11–D14): one forced `submit_plan` call per attempt (temperature 0.4, max_tokens 32000, streaming) under the run's ctx, so each call is a step; a proposal with violations or an unreadable reply goes back as a tool result, at most twice (`repair_attempts`, stage `repairing`). The feedback (`planning/repair.go`) explains each violation in words with the numbers (consumption per link, keep days and last allowed date, cook cells of an H2 day), the cells and keys, and a fix; a reply identical to the previous one is called out, and a lunch or dinner plate without a main sends the plan back as well (`suitability.go`: the slot kind is the slot's `kind` (`light` or `meal`, migration 00042: default `meal`, `slot.breakfast` and `slot.snack` set to `light`; read through `State.SlotKind`, never from name, position or routine cells); roles that count as a main per meal kind are data in `mainRoles`: a standalone recipe is a breakfast only). A side swap whose new side changes the role is sent back too. Calories (`kcal.go`): `planning.DayKcals(State, Target)` is the pure per-day account (kcal per person against the target scaled to the planned non-`none` meals, also for days with nothing proposed); the chooser never repairs a kcal gap (the user picks options for gaps later): a day below 70 % of its target is one run-notes line per run ("Below target: Mon −620 kcal, Wed −410 kcal"). A side swap with no other side of the replaced role gets every side as candidate and the prompt says so (no role advisory then). Before checking, `autofix` grows a proposed session's portions (and frozen portions, for a freezable recipe within the freezer limit) to cover its plates; the change is in the attempt's `autofix` list and in the next feedback. Violations left after that are persisted (`partial`); a provider failure ends the run `error.ai.provider_error`, no readable reply at all `error.ai.invalid_plan`. A request without `chooser` uses the LLM when a provider resolves and the heuristic when none is configured; a configured provider that fails to resolve is `502 error.ai.provider_error` (logged), never a silent fallback. The prompt keeps within 40 k estimated tokens (chars / 4) by leaving out candidates. E2E fixtures: `frontend/e2e/fixtures/chat-scripts/generate-week.json` (a template; placeholders in its `_comment`) and `generate-week-error.json`.

- **Generation runs** (`planning.Service`): a run outlives its request but not the process. `Shutdown(ctx)` (called from `main.go`, bounded to 5 s) refuses new runs and cancels the running ones, which end `error` / `error.server`. A run out of time ends `error.plan.timeout`; saving has its own 30 s budget, so a proposal ready at the deadline is still written. A save that finds the plan changed while the run chose (a replaced draft confirmed or gone, a target cell taken or No plate, a linked session gone) ends `error.plan.changed_during_run` and writes nothing. The window's reservation is freed by deferred calls, even after a panic (logged with its stack). `GET /api/plan/runs/{id}` reports a `running` row the in-memory registry lacks as `error` / `error.server`. Plate outcomes (D25): a restore of drafts (`POST /api/plan/restore`, the Undo of discard) records `restored`, which reopens a discarded run (discarded → open, partially_accepted → accepted).
- **Mid-week re-plan** (`planning/replan.go`, `plate.Service.RemovePlates(plate.Removal)`): the preview and the re-plan share one scan. An uncooked batch whose cook plate goes moves its cook to its earliest remaining plate only when every remaining plate lies in [from, to], none eats from the freezer, and that day has a free cooking occasion (`plan.max_cook_occasions_per_day`, routine cells aside); otherwise the batch is dropped with every component eating it, in or outside the range, and plates left empty go. The preview lists `dropped` plates (`{session_id, food_name, plate_id, date, slot_id, confirmed}`) and `moved` batches (`{session_id, food_name, cook_date, cook_slot_id}`), and every confirmed plate that goes or loses a component is in `confirmed_affected` (so it needs `unlock_confirmed`). `POST /api/plan/replan` returns `regenerate_error` (a message key) when `regenerate` was asked for but its run did not start; the removal stands.

## Coding Rules

- **`errors.Is()`, never `==`** for sentinel errors. Wrapped errors break `==` silently.
- **Domain validation in the service, not the DB.** DB constraints are a safety net only.
- **Sanitize FTS5 input.** Pass user search strings through `sanitizeFTS5()` before MATCH.
- **Use sqlc-generated functions, not raw SQL.** Change query annotations and regenerate if needed.
- **`testhelper.NewTestDB()` must mirror production config** (same pragmas, `SetMaxOpenConns(1)`, etc).

## Testing

**Unit tests:** pure, no DB, no HTTP. Use fakes from `adapters/fake/`.

**Adapter tests:** real SQLite via `testhelper.NewTestDB()`. Never mock the database.

**Migration tests:** `migration_000XX_test.go` in `adapters/sqlite/` — test data shape before and after.

### Coverage Requirements

Every feature must cover happy path **and** edge cases before it's complete:

- Validation: empty/missing required fields, invalid enums, out-of-range numbers, boundary values
- Conflicts: duplicate names, update/delete non-existent, in-use references
- Input sanitization: FTS operators, SQL-sensitive chars, unicode
- Nullable roundtrips: create with value → update to null → verify null
- HTTP edge cases: malformed JSON, non-numeric IDs, invalid query params

## Worktrees

Inside `.claude/worktrees/*`, prefix Go commands with `GOWORK=off` (e.g. `GOWORK=off go test ./...`). The root `go.work` created by `mise run lsp` lists only the main checkout's `./backend`, so without it Go fails with "directory prefix . does not contain modules listed in go.work".

## SQLite Gotchas

- Pragmas are per-connection. `sql.DB` pools — use `SetMaxOpenConns(1)` so all queries share WAL + `busy_timeout`.
- Timestamps: stored as `TEXT` via `datetime('now')`, Go parse layout `"2006-01-02 15:04:05"`, serialize as RFC3339 in API responses.
