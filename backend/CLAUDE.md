# Backend — Plantry

Go binary (module `github.com/jaltszeimer/plantry/backend`). Must cross-compile to ARM with no CGO — use `modernc.org/sqlite` (pure Go), never `mattn/go-sqlite3`.

## Commands

All commands run from `backend/`:

```bash
go build ./...                        # compile
go test ./...                         # all tests
go test -run TestName ./path/...      # single test
go vet ./...                          # vet
golangci-lint run                     # lint
sqlc generate                         # regenerate from queries + schema
go test -race ./...                   # race detector — run before feature complete
scripts/check-sqlc-usage.sh           # every sqlc query needs a non-test caller
go tool deadcode -test ./...          # unreachable functions (pinned x/tools); the gate ignores sqlcgen/
go run ./cmd/plantry backup -out F    # consistent copy of the database + secret.key (see Backup)
```

`go tool deadcode -test ./...` must report nothing outside `internal/adapters/sqlite/sqlcgen/`; `scripts/gate.sh` and `backend.yml` run it, with the tool version pinned in `go.mod`. Remove the dead function instead of keeping it. The gate also cross-builds `GOOS=linux GOARCH=arm64` and `GOARCH=arm GOARM=7` (`CGO_ENABLED=0`), so a CGO or arch-specific dependency fails there.

`scripts/check-sqlc-usage.sh` fails when a `-- name: X` in `internal/adapters/sqlite/queries/*.sql` has no `.X(` in a non-test `.go` file outside `sqlcgen/`. It runs in CI and in the repo-root `scripts/gate.sh`; delete the query instead of keeping it unused.

## Architecture — Hexagonal-Lite

Data flow: `transport → domain ← adapters`

**Aggregates** are plain exported structs. `*.Service` holds business logic and takes repo interfaces as constructor args — never concrete types.

**sqlc workflow:** edit `queries/*.sql` → run `sqlc generate` → implement/update `*_repo.go` using generated functions. Never write raw SQL outside of query files.

**Safe table rebuild.** Dropping a table with foreign keys on cascade-deletes its dependants (00014/00016 did on old installs). Rebuild tables (e.g. to add `AUTOINCREMENT`, as 00030 for `plates`/`cook_sessions` and 00033 for `presets`) in a Go migration registered with `goose.AddMigrationNoTxContext`: pin one connection with `db.Conn`, `PRAGMA foreign_keys = OFF` on it, copy in one transaction, run `PRAGMA foreign_key_check` before commit, restore `foreign_keys = ON` afterwards, and recreate triggers the drop removed. Give sqlc the end-state schema in `db/schema_patches/`.

**Migrations** use goose. Numbered SQL files in `db/migrations/`. Go migration files (`.go`) handle complex data transformations. Migrations run automatically at startup (`goose.Up` in `main.go`) — no manual step needed.

The profile (`domain/profile`) also carries `diet_type`, `meat_days_per_week_max` and `household_portions` (00023), and (00045) the nutrition goal `goal` (`maintain` default / `lose` / `gain`; absent in `PUT /api/profile` keeps the stored one) and optional body data `weight_kg`, `height_cm`, `birth_year` (a year, not an age: it does not go stale), `sex` (`female`/`male`/null) and `activity_level` (PAL 1.4 / 1.6 / 1.8). They are a full replace (null clears), validated in `profile.validate` (`error.profile.invalid_goal`, `invalid_body_data`); a `kcal_target` below `profile.MinDailyKcal(sex)` (1500 for male, else 1200, also with an unknown sex) is `error.profile.kcal_below_floor` on every save (reading a stored lower target still works; the user raises it to save). The kcal target stays the user's own number; the "suggest my target" estimate (Mifflin-St Jeor x PAL) is computed in the frontend (`lib/nutrition-estimate.ts`).

**Nutrition policy** (`planning/policy.go`, `PolicyOf(planning.Profile)`): the one place for the kcal tolerances, replacing the old `KcalBandLow/High`. Day band (S2) / week band (S4): maintain 90-110 % / 95-105 %, lose 90-105 % / 95-103 %, gain 95-110 % / 97-105 % of the scaled target (the lose/gain week bands and the day band widths are professional-practice inference; sources in the code comment). Floor (hard rule **H9** `kcal_below_floor`, `index.h9`): a complete day with a plate of the target, nutrition data and a kcal target must hold at least `max(75 % x scaled target, absolute floor x planned/all meals)` kcal per eater; the absolute floor (1500 male, else 1200, secondary sources) scales with the planned meals like the target, less routine cells that hold no plate (`DayKcal.FloorShare`). On the board H9 shows only from today on and as a warning on days without a draft plate (`BoardIssues`). H9 is in `Check`, in the board's issue filter (H1, H2, H5, H8, H9), in the repair feedback (`repair.go`) and in `Score.HardViolations`. **Weekly ledger**: `Evaluation.Week` (`{days, avg_kcal, target_kcal, pct}`: the complete days S2 judges, average kcal against the average scaled target; nil without a target or such a day) is in the run log's `plan.evaluation`, the compact `evaluate_plan` / `get_plan` result (whole window, never narrowed to the touched days) and `apply_changes` `after.week`. Soft issue S4 `week_kcal_below_band` / `week_kcal_above_band` (no date, no options) needs at least 3 complete days. The prompts say it with `Policy.Describe()`: the target is a target, the week matters most, the floor is hard (planner prompt `p10`, chat prompt `v11`). **Protein and macros (00046, planner `p11`, chat `v12`, heuristic `h10`)**: with `weight_kg` the protein target is g per kg (`Policy.ProteinGPerKg`: maintain 1.0, lose and gain 1.6, at least 1.0 from age 65 (also over a lower override, which is raised to 1.0), optional profile override `protein_g_per_kg` validated 0.8-2.2 (2.2 is an unverified upper bound), never below the DGE 0.8; sources in the `policy.go` comment), scaled to the planned meals like the kcal target (`DayEval.protein_target_g`); a day under 90 % of it is S3 `protein_below_target` (params `protein_g`, `target_g`, `min_g`; its options must raise the day's protein grams), replacing the share margin; without a weight the `ProteinPct` share logic is unchanged. `Evaluation.Week` also carries `avg_protein_g`, `target_protein_g`, `protein_pct`, `carbs_pct`, `fat_pct` (kcal-weighted) and `fiber_g` (average per day, display only, DGE 30 g; absent when no food has fibre data or any food on the counted days lacks it, since a missing fibre value reads as 0 and a partial average would mislead). With 3+ complete days: S3 `week_protein_below_target` (average under 100 %) and soft S5 `week_carbs_out_of_range` / `week_fat_out_of_range` (AMDR carbs 45-65 %, fat 20-35 % of energy, or the user's `carbs_pct` / `fat_pct` +-5 points), no date, no options; S5 applies to every user (it does not depend on the weight) and ranks last, after preferences and never at the cost of kcal or protein. Heuristic `closeProteinGaps` (after the floor pass, needs a kcal target and a weight): up to 2 verified no-cook adds per day under 100 % of the day target (S3 day issue stays < 90 %), at most 1 per plate, lunch and dinner before stacking, no food twice a day, the most protein first (adds that stay at or under the day target first), with diet type, the day band, the running week average under the week band top and every hard rule checked by `verify`; a day nothing lifts gets the run note "Protein below target". **Light intent (planner `p12`, chat `v13`, heuristic `h11`; `planning/light.go`)**: a light request is structured data, a list of `{date, scope: meal|day, slot?: lunch|dinner}` (`planning.LightIntent`, `ValidateLight`), not free text. The intents are stored per date in `plan_light(date, scope, slot)` (migration 00047, sqlc `plan_light.sql`, `sqlite.PlanLightRepo` = `planning.LightStore`) and `Builder.Build` loads the window's rows into `State.Light`, so the board, the chat prompt/`chatView`/`get_plan`, `evaluate_plan` and every run (the HTTP heuristic regenerate too) stand under them without being told again; every `plan.evaluation` step carries them (`Evaluation.light`), the run's `scope_json` and `plan.context` list the request's own. A call that is given `light` for a date **replaces** that date's stored intents (`MergeLight`; `scope: none` only clears the date, the chat tools' clear shape). Input: `submit_plan` / `evaluate_plan` `light`, chat `apply_changes`, `get_plan` and `regenerate` `light` (a tool-call ctx value merged over the stored ones by `evalWindow`), `planning.Request.Light`. Saved: a successful planner run writes the effective light of its window (`merged.Light`, inside the save transaction) and a non-dry-run `apply_changes` writes its own (`saveLight`); past dates are pruned on every write (`LightStore.Replace`). Rejected back to the model (`ResolveLight`; tool error `ErrInvalidInput`, or the chooser's repair feedback): a date outside the window, a `meal` slot the plan has no slot for (custom slot names), and more than `MaxLightDays` (3) day-scope intents in a window once merged with the stored ones (the message points to the profile goal `lose`); meal intents are not capped. Run notes echo the light in plain words in the notes' language (`lightNote`: "Light: Tue dinner, Thu day" / "Leicht: Di Abendessen, Do Tag"). The tool schema is one definition, `planning.LightSchema(withClear)`. A light day's target is clamped at the floor in `DayKcals` (a lose-mode target of 1600 asks for 1500, not 1360, so S4 is not raised by a day held at the floor); S6 is not raised on confirmed plates or routine cells. **`meal`**: that lunch or dinner holds at most 75 % (`LightMealShare`) of its normal share (`DayKcal.Scaled / planned meals`, the even split) and the day target is unchanged; soft issue S6 `meal_not_light` (params `kcal`, `max_kcal`, `normal_share_kcal`) when it is not lighter. **`day`**: the day's target is 85 % (`LightDayShare`, `DayKcal.Adjusted`) and its S2 band is centred there (`DayEval.target_kcal` is the adjusted one, `normal_target_kcal` the normal one, `light` is `meal|day`); H9 and the absolute floors stay on the normal target. `Week.target_kcal` is the average of the adjusted day targets (S4 measures against it, so honouring the wish does not raise S4), `Week.normal_target_kcal` the normal average (only when it differs). Both prompts say it with `Policy.Describe()`: light means `meal` unless the user explicitly asks to eat less for the day or week, never below the floors, say so in the reply when a floor stopped a lighter day. Heuristic: a light cell ranks recipes over its reduced share last, takes a side only while the plate stays within the share, never grows or adds to a light meal's plate (`editablePlates`, `topUpDay`) and the other meals of a light-meal day are topped up to the day band's low end. The HTTP generate/regenerate bodies do not take `light` yet and the board shows no light mark (plan-board PR).

## Availability

Migration `00024_availability.sql`, package `domain/availability`. A cell is (date, slot) and its mode is `plan`, `routine` (needs a `preset_id`; a label only for now, nothing applies the preset) or `none` (No plate). It resolves as per-date override → weekday default (weekday 0 = Monday) → `plan`. `plan` defaults are never stored.

- `GET /api/availability?from=&to=` — resolved cells with `source` (`override` / `default` / `fallback`), at most 62 days.
- `GET` / `PUT /api/availability/defaults` — `{items: [{weekday, slot_id, mode, preset_id}]}`; PUT replaces the defaults of all active slots.
- `PUT /api/availability/{date}/{slotId}` — `{mode, preset_id?, note?, remove_plate?}`. `none` on a cell with a plate is `409 error.availability.cell_has_plate` unless `remove_plate` is set; then the plate is deleted through `plate.Service.Delete` in the same unit of work and the response `{cell, removed}` carries the `PlanSnapshot` that restores it (`POST /api/plan/restore`; `removed` is null when nothing was removed). `DELETE` clears the override.

A cell holds at most one plate: migration `00025_plates_cell_unique.go` turned the old per-plate skip flag into `none` overrides (with its note), merged duplicates, dropped the flag column and made `(date, slot_id)` unique. Creating or moving a plate into a `none` cell is `409 error.plate.cell_unavailable`; into an occupied cell, `409 error.plate.cell_occupied`. The agent sees `none` and `routine` cells and must not plan them.

## Plan window and read models

Package `domain/window` (pure): a window is the 7 days starting on `plan.shopping_day`. `Containing(date, sd)` starts on the latest shopping day ≤ date; `Anchored(today, anchor, sd)` is the window containing today (`today`) or starting on the first shopping day ≥ today (`next_shopping_day`).

Package `domain/planview` builds the read models; it never writes and takes its dates as arguments. Plates load with one `ListByDateRange` call for the whole range and sessions with `CookSessionRepo.ListInRange` (two queries), never per plate.

- `GET /api/plan?start&today` — the window at `start` (must be a shopping day, else `400 error.plan.invalid_start`) or the anchored one: `window`, active `slots`, `cells` (date × active slot with availability and plate), `sessions` (cooking in the window or linked to a plate in it), `days` (per-eater macros with `complete`/`missing`), `targets` (null without a kcal target), `stats`, `issues` (`planning.Check` over every cell of the window, filtered to H1, H2, H5 and H8, with diet classes from `food.Service.DeriveDiet`; `missing_plate` only while the window has drafts and only for cells dated today or later), `draft` (`{plates, sessions, run_id, notes, chooser}` of the newest run with drafts in the window, read through the `RunNotes` port; null without drafts) and `running_run_id` (from the `Progress` port; null while none is wired). The state for `planning.Check` uses the planner's row mappers (`planning.StatePlate`, `StateSession`, `StateCell`, `StateProfile`, `BaseFacts`, `ReadSettings`), so the board and the generator check the same state (`TestStateParity_BoardAndBuilder`). Only while the window has drafts does H8's candidate list load: the recipes not eaten since `planning.VarietySince` (sqlc `ListUneatenRecipes`, one query), with diet classes only when `planning.DietRestricts` the profile's diet type. Day macros resolve in one `PerPortionDetailedMany` batch.
- `GET /api/today?date&today` — confirmed rows only (D26); `verdict` (`draft_only` when the date has no confirmed plate and the window has drafts, `no_plan`, `no_plates`, `cook`/`quick_cook` for the uncooked main with most portions, ≤ 20 min is quick, else `nothing_to_cook`), `cook`, `meals`, `reminders` (`defrost`, `use_by`), `rate`, `plan_banner` and `setup`.
- `today` defaults to the server's local date; `date` defaults to `today`.

## Unit of work

`domain.Transactor` (`domain/transactor.go`, D21) is the port; `sqlite.TxRunner` (`adapters/sqlite/tx.go`) implements it. `InTx(ctx, fn)` runs `fn` in one transaction whose `*sql.Tx` travels in `fn`'s ctx, and every repository called with that ctx joins it. A nested `InTx` joins the outer one: there are no savepoints, so a failed nested call leaves its partial writes in the outer transaction and the caller must return the error. Multi-write operations (plate mutations, availability `none` with `remove_plate`, preset apply) run inside one `InTx`, and so do the `/api/plan` and `/api/today` read models, so a concurrent write cannot tear them.

Every domain sentinel's i18n message key lives in `domain.MessageKey` (`domain/errors.go`; the plate quantity sentinels in `plate.MessageKey`); the HTTP error map adds only the status, and the agent's tool errors use the same keys. A test fails when a sentinel in `errors.go` has no key or no status.

## Plate aggregate and write path

`plate.Service` (`domain/plate/service.go`, built with `plate.NewService(plate.Deps{...})`) is the single write path for plates, plate components and cook sessions. Handlers, the agent tools and preset apply/copy all go through it.

- A cell (date, slot) holds at most one plate. A plate has `eaters` (default: the profile's household portions) and ordered components; a component is a food with `portions` per eater, or for a leaf `amount` + `unit`.
- A composed component is linked to a cook session. Without a given `CookSessionID` a new component gets a fresh session at the plate's own cell. Mutators: `Create`, `Update`, `Delete`, `ClearRange`, `AddComponent`, `UpdateComponentQuantity`, `SwapComponent`, `RemoveComponent`, `Apply`.
- `Delete`, `ClearRange` and session deletion return a `PlanSnapshot` that restores them; `Apply(snapshot, ApplyOptions)` writes one (D22). `Apply` decides every plate's placement before it writes anything, so a conflict (an occupied cell without overwrite, a duplicate cell in the snapshot) fails the whole call. Snapshot refs are strings (`"s1"`), snapshot components carry `sort_order`, snapshot plates an optional `plate_id`. Preset apply and copy-week build snapshots and call `Apply`.
- `DELETE /api/plan?from&to&slot_id` is slot-scoped (`ClearRange`).

### Sessions and D11

A `CookSession` (`domain/plate/session.go`) says "food X is cooked at (cook date, cook slot), producing `portions`", with `frozen_portions`, `cooked_at` and a note. Components link to it as `fresh` (own cell), `leftover` (later within keep days) or `frozen`; links are ordered in cell order (date, slot `sort_order`, slot id; D12). `plate.BuildView` / `SessionView` add links, consumption and warnings (`leftover_before_cook`, `past_keep_days`, `deficit`, `frozen_deficit`; D13).

D11 (`plate.Sync`): when a change alters what a session's links consume, a session that exactly covered its links before still covers them exactly after; one with a surplus or deficit keeps its portions; frozen portions never exceed portions. The service tracks every session a mutation touches (`tracker`) and settles once at the end: a session without links is deleted, the others follow D11. Explicit edits (`SetSessionPortions`, `SetCooked`, `AddLeftovers`, `DeleteSession`) always win over D11. Freezing needs `plan.freezing_enabled` and a recipe not marked unfreezable (D14). `LeftoverCells` suggests the next cells for leftovers.

## Units and rounding

`domain/units` (`round.go`): `Display(amount, unit)` rounds an exact amount for reading (D26). Metric mass/volume work in g/ml, rounded to 1 below 100 and to 5 from 100; from 1000 they switch to kg/l only for clean multiples of 100 (1500 g becomes 1.5 kg, 1235 g stays). tbsp/tsp round to 0.5; everything else, counts included, stays exact. `ToBase` converts metric units to g/ml so sums add up. `Buy` rounds a count unit up to whole units. `CountGrams` is the only count-to-gram table. Amounts are stored and summed exact; round only for display.

## Food history and list filters

Eating history is derived, never stored (D16): `food.Service.Derive(ctx, today, foods...)` sets `LastEaten` and `TimesCooked` on composed foods and `UsedInCount` on leaves, with one query per kind (sqlc `FoodHistory`, `UsedInCount`). Plates marked `not_eaten` and draft rows do not count.

`GET /api/foods` filters: `max_minutes`, `not_eaten_weeks`, `created_within_days`, `today`, `sort=name|last_eaten|created` (`last_eaten` ignores favorites). Recipes carry `last_eaten` (`YYYY-MM-DD`), `times_cooked` and `per_portion` (batched `PerPortionDetailedMany`); leaves carry `used_in_count`. Plate feedback statuses are `loved`, `disliked`, `not_eaten`; others are `400 error.feedback.invalid_status`. `GET /api/foods/macros` serves the plate sheet's macro preview. `GET /api/foods/{id}/scaled?portions=` (required, 0 < p <= 100) returns the scaled ingredient list.

## Diet class

Package `domain/diet` (no domain imports): `Class` (`vegan` < `vegetarian` < `pescetarian` < `omnivore`, plus `unknown`), `Order`, `Valid`, `Max` (any unknown child, or none, gives unknown), `Compatible(class, dietType)` (class ≤ type; unknown never) and `Classify(name)`, a 3-stage data-driven en/de keyword classifier: phrases like "Kokosmilch" add their class and are cut out of the name, then markers like "vegan" or the animal keywords run on the rest, and the result is the max of everything found (else a plant keyword → vegan, else unknown); umlauts and ß are folded.

Migration 00035 adds `foods.diet_class`, an override only (NULL = derived, nothing backfilled; D28). `food.Food` carries `DietOverride` (stored) and the derived `DietClass`/`DietClassSource` (`auto` leaf name, `user` override, `derived` recipe max over its children). `food.Service.Derive` sets them (`DeriveDiet`: one `LoadTrees` for all recipes without an override); `food.SetDietClasses(nodes)` does it on an already loaded tree.

- Every food JSON has `diet_class` and `diet_class_source`; scaled ingredients and import draft ingredients carry `diet_class`.
- `GET /api/foods?diet=<class>` keeps foods with class ≤ it, unknown excluded. The class is not stored, so the service filters after the SQL query and pages afterwards.
- `PUT /api/foods/{id}/diet-class {class | null}` sets or clears the override (both kinds); error `error.food.invalid_diet_class`.

Plate feedback (spec §6.6): loved/disliked move the plate's recipe tags into `likes`/`dislikes` and out of the opposite list; role names and `explore` are skipped.

## Plan generation

Package `domain/planning` turns "plan my week" into a checked draft: context assembled in Go, one proposal from a chooser (LLM or heuristic), the checker, a bounded repair loop, then drafts persisted. The HTTP handlers (`handlers/plan_generate.go`) and the chat agent's `regenerate` tool (D8) call it.

- **Checker.** `planning.Check(State, Target) []Issue` applies the hard rules H1–H9 to a pure `State`; `Merge(State, Target, Proposal)` lays a proposal over the fixed context (proposed plates get negative ids, sessions keep their key); `ComputeScore` and `ToSnapshot` complete the pipeline. Issue codes beyond the spec's: H1 `extra_plate`, `missing_plate`; H6 `confirmed_in_target`, `session_outside_target`; H7 `unknown_food`, `unknown_session`, `not_composed`, `session_food_mismatch`, `duplicate_session_key`, `invalid_portions`, `plate_without_components`, `plate_outside_target`, `plate_on_confirmed_cell`. H8 (variety) judges only the **proposed** (unconfirmed) cooks of a run: confirmed rows and routine cells are never subject to it, and it relaxes to the `variety_relaxed` warning when fewer eligible mains exist than cooks. `GET /api/plan` runs the same `Check` and filters to H1, H2, H5 and H8.
- **Scopes (D6).** `window` (generate), `day`, `plate`, `side` and `empty_cells`; `Scope.From`/`To` bound `empty_cells` (the re-plan). Everything outside the scope and everything confirmed is fixed context. Use the name `empty_cells`: the frontend legacy gate bans `fill_empty`/`replace_all`.
- **Endpoints.** `POST /api/plan/generate {start, chooser?, instruction?, eaters_by_date?, include_new_recipe?}` and `POST /api/plan/regenerate {scope, start, chooser?, instruction?}` return `202 {run_id}` (`?today=` is the client's date). `GET /api/plan/runs/{id}` returns status, `stage`, counts, issues, score and window; the client polls it, there is no SSE (D9). Regenerate keeps each day's eaters (guests) and never asks for a new recipe. Fewer than `setup.RecipeTarget` composed recipes is `error.plan.not_enough_recipes`; a second run on a window is `error.plan.generation_running`. `POST /api/plan/accept` and `/discard` `{from, to}` act on the window's draft closure (accept returns `{plate_ids, session_ids}`, the body of `POST /api/plan/unaccept`; discard returns `{removed}`, which `POST /api/plan/restore` brings back as drafts); `POST /api/plates/{id}/confirm|unlock` and `/api/cook-sessions/{id}/confirm|unlock` move one row's closure. Confirmed wins wherever a link joins different states.
- **Runner.** A generation is asynchronous: `start` validates, picks the chooser, reserves the window in `planning.Progress` (the in-memory registry; one run per window), creates the `ai_runs` row and runs in a goroutine on a **detached ctx** with a 3 minute timeout (`runTimeout`). A panic ends the run as an error instead of the process. Stages (D35): `resolving`, `choosing`, `checking`, `repairing`, `saving`. `Progress.Running(start)` feeds `running_run_id` on `GET /api/plan`, which is how a reloaded board re-attaches. `Service.Wait` lets shutdown wait for running runs; `Service.Await(ctx, id)` blocks until one run finished (a per-run done channel in `Progress`, closed after the row is finished) and returns ctx's error when ctx ends first; `Deps.Go` lets tests run synchronously. At startup `FailInterruptedRuns` ends `running` rows left by a crash as errors (logs `ai.run.interrupted`). A run with no open `plan` cell skips the chooser (routines are still applied; it ends `ok`, cost null).
- **Chooser selection.** `Deps.Choosers` maps `airun.ChooserLLM` / `ChooserHeuristic`. A request **without `chooser`** uses the LLM only when a provider resolves (the chooser's `Ready`), else the heuristic. Explicit `llm` without a provider is `503 error.ai.provider_missing`; a provider that cannot be built is `502 error.ai.provider_error`; a reply that never yields a readable plan ends the run `error.ai.invalid_plan`. The e2e backend always has the fake provider, so heuristic e2e requests must pin `chooser: heuristic`.
- **Heuristic** (`heuristic.go`, run-log version `h12` = `planning.HeuristicVersion`): deterministic, no AI. The first day cooks at its earliest cell; later days cook at dinner and the earlier cells eat leftovers (sessions grow within keep days). Leftover plates (a batch's cover and later cells eating a session) respect `meat_days_per_week_max` (h6); only a cell nothing else can fill takes a meat leftover. Bump the version when it changes what it picks. A lunch or dinner (slot kind `meal`) is cooked only with a recipe of role main: with none available the cell stays empty (a run note, H1 reports it), and a leftover that has to exceed `meat_days_per_week_max` to fill a cell is allowed only with a run note (h7); a cell left empty by the day's cooking cap makes the heuristic rerun with a cook forced on the latest earlier cell whose leftovers reach it (h8: batch-closure cells of a regenerate are refilled). h9/h12: `topUpFloors` (`heuristic_floor.go`) lifts every complete day in order: (1) under its H9 floor up to it (portions of proposed mains and carb sides, and their sessions so H3 holds, round up; then verified no-cook foods, S2's `candidates` + `verify`); (2) `closeProteinGaps` when a g/kg target is active; (3) under its S2 band low end up to it, while the week stays under its target; (4) while the week average is under its target, the days furthest under go up toward it by at most what the week still lacks (portions round down). Growth is at most 1.5x of the planned portions over all passes (`topUpBase`), light meals never grow, a food is not added twice a day, and with a protein target kcal fillers go by protein per kcal. Days the recipes already overfill are not shrunk. A day still under the floor stays an H9 (`floorNote`) and a day under the band gets the run note `kcalNote` ("Below target"), also for the LLM chooser. Measured on the eval library (one person, yoghurt routine): week 100 / 101 / 100 % at 1800 / 2000 / 2500 kcal (h11: 93 / 89 / 82 %).
- **Compact model-facing evaluation (`planning/evalview.go`).** `Evaluation.Compact(View)` is what the model gets from `evaluate_plan`, the repair feedback, chat `get_plan` and (days, plates, sessions, issue delta through `planning.Compact`) chat `apply_changes`; the run log's `plan.evaluation` steps stay the full `Evaluation`. Rules: only the days the call touched (planner: the days with a proposed plate, `ProposedView`; `get_plan`: the requested range; `apply_changes`: the touched dates), their plates, and their soft issues (hard issues and warnings stay wherever they are); plate components in full only on the plates the call proposed (planner: the proposed plates, negative id); `get_plan` (`View.Slim`) and the `apply_changes` touched plates' `component_details` carry slim components (`planning.SlimComponents`: `plate_component_id`, `name`, `portions`|`grams`, `kcal`, `protein_g`, `nutrition_complete` only when false; food, role and session are in the cells), so judging a plate needs no second call; kcal rounded to integers, every other number to one decimal; every zero, false, null and empty field omitted (absent = 0 / false / none) except `issues`, `totals`, `violations`, `warnings`, `soft`, `meat_days`; `complete` and `nutrition_complete` are shown only when false (they are true by default); an issue option drops the fields its `op` repeats (`food_id`, `date`, `slot_id`, `plate_id`, `portions`, `grams`) and keeps `action`, `name`, the deltas, the day figures and `op`; `autofix` only when Go corrected the plan. Each tool description documents its shape. Measured by `TestCompactEvaluationPayload` (`internal/eval`, family_daily week; run with `-v` for the byte counts of the full evaluation, the planner's result, `get_plan` and a one-day `apply_changes`; the issues with their options are most of what is left). `evaluate_plan`'s issues are the hard violations and warnings of the whole plan plus the soft ones of the listed days, and `totals` counts exactly the issues listed (the tool description says so). Issue `params` are pruned like every other field (a `count: 0` is absent).
- **Soft rules and options (`planning/soft.go`, severity `soft`).** `planning.Evaluate` reports them next to the hard rules; they never block saving and are not repaired. S1 is the existing H5 `meat_days_exceeded`. S2 `kcal_below_band` / `kcal_above_band`: a day's kcal per eater outside the policy day band of its scaled target (`Policy.DayLow` / `DayHigh`, see Nutrition policy; the run note "Below target" uses the same band). S3 `protein_below_target`: protein share below the profile target minus `ProteinMarginPts` (5). Below-band and S3 issues carry `Issue.Options` (max 3, computed in Go, ranked by whether they bring the day into the band, then protein share gain, then fit): add a no-cook side or snack (leaf at `TypicalLeafGrams` = 100 g, or a recipe with 0 cook minutes) or raise the portion/grams of a component already on the day, each with `kcal_delta`, `protein_delta_g`, `day_kcal`, `day_protein_pct`, `cook_occasions`, `new_meat_day`. Each option is verified by re-running `Check` on a copy: no new hard issue (H2 is never worsened), the day stays under the band top, S1 not exceeded, an S3 option strictly raises the day's protein share, an S2 option moves the day's kcal closer to the target. Each option carries `op`, an `apply_changes` op as it is (`add` with `plate_id` or `date`+`slot_id` and `portions` or `amount`+`unit` g, or `set_quantity` with `plate_component_id`). **Above-band kcal issues carry no options** (decision: nothing the code can add helps).
- **No-cook detection (decision).** `planning.NoCook(*food.Food)` (`nocook.go`) is a derived heuristic because no flag is stored: a leaf counts when its shop section (override or `shopping.Classify`) is produce, dairy or bakery and its name is not a cooked-first word; a recipe counts when its cook minutes are explicitly 0 and it is not a main. A stored per-food override is planned for later. `State.NoCook` lists the ids and `FoodFacts.NoCook` carries the flag; `find_foods no_cook` and the planner's no-cook table use it.
- **`evaluate_plan` (planner, p7; compact result).** The LLM chooser offers `evaluate_plan` (same input schema as `submit_plan`, saves nothing) and `submit_plan` with `tool_choice` auto (`ToolChoice` nil) plus a system line. Up to 8 evaluations per run (`maxEvaluations`) and a hard bound of `maxModelCalls` provider calls per run (evaluate_plan replies and repairs included): past it the run ends with the last submitted proposal (partial, run note) or `error.ai.invalid_plan` when none was submitted; each returns the `Evaluate` result for the merged proposal in the compact model-facing form (below) and is recorded as a `plan.evaluation` step with phase `dry_run` (the stored step keeps the FULL `Evaluation`, so audits lose nothing). A `submit_plan` repair feedback appends the same compact JSON. A proposal component may be a leaf with `grams` (`Merge`, `ToSnapshot` writes amount + unit g; H7 allows grams for a leaf only). The fake client's `for_tool` turn also matches an offered tool when `ToolChoice` is nil, so scripted `submit_plan` e2e turns still work.
- **LLM chooser** (`llmchooser.go`, `prompt.go`): see AI run log. Prompt version `p12` (p12: light intent, see Nutrition policy; p9: do not add up kcal, protein, meat days or keep windows in reasoning, call `evaluate_plan`; p8: one paragraph on calling `evaluate_plan` from code to compare drafts; p7: `evaluate_plan` before `submit_plan`, soft rules S1-S3, a no-cook table and a `meat` column, leaf `grams` in proposals; p6: no kcal-gap repair wording, portions are usually 1; p5: the task states the fill-cell count and lists the cells, fixed cook cells are listed as occasions, candidate rows carry `suits`, a side swap keeps the role and shows the plate's other components, per-day scaled kcal budgets; p4: per-eater portions, keep table, repair feedback with numbers and fixes, autofix; p2 added the user's recipe swaps of the last 4 weeks, read from `plate_events` by `Corrections`, D21); bump `PromptVersion` on every prompt change. The repair loop lives inside the chooser (at most 2 repairs, stage `repairing`, plus one extra attempt that does not use the budget: the first reply is a skeleton (an H1 `missing_plate`-only plan or one missing half of the fill cells, counted from the empty plan cells, not `Target.Cells`), at most once per run and only for call 1, recorded in the run notes). The worst case is 1 + 1 + 2 calls.
- **Persisting.** Generated plates and sessions are written through `plate.Service` as `draft` with `actor.Generator` and the run's `ai_run_id`. A generator plate linked to a confirmed session is created confirmed, so never delete it in cleanup; count it as kept. `plate.Service.RemoveDrafts`, `DraftClosure` and `PlateClosure` support regenerate.

### Mid-week re-plan

`GET /api/plan/replan/preview?from&to[&none=date:slot…][&today]` returns `{none_cells, confirmed_affected, spare}`: the No-plate cells that hold plates, the confirmed plates a re-plan would remove, and the batches that would cook more than is still eaten (`spare[]` with `portions`, `freezable`, `mutable`; a batch is mutable only when it is not cooked and cooks on or after `from`, and only a mutable one can be reduced; `freezable` also holds for cooked ones, while `plan.freezer_keep_days` from their cook date have not run out at `from`).

`POST /api/plan/replan {from, to, none_cells, unlock_confirmed, spare: freeze|keep, regenerate, chooser?, instruction?}` returns `{removed, run_id, unassigned}`. A cooked or earlier batch's freed portions are frozen when freezing is on and the recipe freezable (portions stay, frozen grow); portions that end up eaten by no plate are `unassigned` (preview `spare[].unassigned` counts them for a freezing re-plan). **`none_cells` is part of the contract**: the re-plan writes the No-plate overrides itself in the same transaction, because the availability API refuses `none` on an occupied cell. Confirmed plates need `unlock_confirmed`, else `409 error.plan.confirmed_affected` lists them; `from` before `?today=` is `400 error.plan.replan_past`. Days before `from` and cooked portions are never touched. The server's only sources of "today" are `?today=` and its clock. The window is reserved from before the removal until the run starts, so no other generation slips in between; if the run fails to start after the commit, the error is logged and `run_id` is null. `removed` alone cannot undo a re-plan (the overrides and the new run are not in it), so a re-plan has **no Undo**.

`plate.Service.RemovePlates(ctx, ids, keep)` is the removal primitive: one unit of work; each session in `keep` ends with exactly its (frozen) portions and survives without links, so a cooked batch is never deleted; other sessions follow D11. An uncooked session that loses the plate on its cook cell but keeps other links **moves its cook to the earliest remaining plate** in the same transaction (a session update event; this can add an H2 on the new day, accepted). A missing plate is `ErrNotFound` and nothing is removed.

### Offline eval

`internal/eval` and `cmd/plantry-eval` run plan generation offline (spec §8.4): an embedded 30-recipe library (`library.json`) and eighteen scenarios (`internal/eval/scenarios/*.json`), each run on a fresh in-process database copied from a migrated template, through services wired like `main.go`. A scenario's expectations: `evaluation` (asserts on the saved plan's closing `plan.evaluation`: `week_pct`, `week_protein_pct_min`, `min_day_share`, `light_adjusted`, `issues_present`/`issues_absent`, `notes_contain`; the nutrition scenarios `nutrition_maintain` (2000 kcal), `nutrition_maintain_2500`, `nutrition_lose`, `light_meal_weekday_dinners`, `light_day`, `protein_gap_week`, `unreachable_floor`; a step takes `light`, the profile `goal`/`weight_kg`/`sex`), `allow_violations`, `min_plates`, `no_plate`, `kept_confirmed`, `unchanged_before`, `frozen_spare`, `min_repeats`.

```bash
go run ./cmd/plantry-eval                                   # all scenarios, heuristic chooser, 3 runs each
go run ./cmd/plantry-eval -scenarios family_daily,away_thu_fri -runs 5
go run ./cmd/plantry-eval -chooser llm -prompt-version p7   # scripted LLM mode, no network
PLANTRY_EVAL_LIVE=1 PLANTRY_AI_PROVIDER=anthropic PLANTRY_AI_API_KEY=... \
  go run ./cmd/plantry-eval -chooser llm -model <model>     # live: real provider, costs money
go run ./cmd/plantry-eval -compare earlier.jsonl            # per-component diff against an earlier report
```

Flags: `-scenarios` (comma-separated, default all), `-chooser` (`heuristic` or `llm`), `-runs` (default 3), `-model`, `-prompt-version`, `-out` (JSONL, default `plantry-eval.jsonl`, gitignored), `-compare`, `-keep-db <dir>` (keeps each run's database as `<scenario>-<run>.db` with its run steps for audit; default: removed; a live run (`PLANTRY_EVAL_LIVE=1`) always keeps them: without `-keep-db` they go to `plantry-eval-dbs/<timestamp>/` (gitignored) and the path is printed). Scripted LLM mode feeds the heuristic's proposal through the real `LLMChooser` and its `prompt_dates` check. Live mode needs `PLANTRY_EVAL_LIVE=1`, `PLANTRY_AI_PROVIDER` (`anthropic` or `openai`), `PLANTRY_AI_API_KEY` and a model (`-model` or `PLANTRY_AI_MODEL`). The command prints a summary, writes one JSONL record per run and exits non-zero when a run failed an expectation (the report is still written). `cmd/plantry-eval/testdata/compare.golden` is rewritten with `UPDATE_GOLDEN=1 go test ./cmd/plantry-eval/...`. Re-run the suite after changing the heuristic, the checker or a prompt, and `-compare` against the previous report.

## Shopping list

Package `domain/shopping`; `GET /api/shopping-list` returns sections in walk order. Rules:

- Confirmed rows only; `include_drafts=true` adds draft sessions and draft leaf plates, and `has_drafts` reports whether the range has any either way.
- It buys the cook sessions' `portions` (not what plates consume) plus leaf components (amount × eaters), for the range's dates. The default range is `ShoppingDefault` of the anchored window; `from`/`to` override it inside the window containing `from`.
- Amounts sum in metric base units (`units.ToBase`); `display` is in the contributions' unit when they share one, otherwise grams; `buy` is set for count units only.
- `used_in` lists the sessions or leaves an item is bought for, in cell order; `draft` marks a use from a draft session or draft plate (only with `include_drafts`).
- Sections are the `food.ShopSections` enum (`domain/food/shop_section.go`). A food's `shop_section` column (migration 00031) overrides `shopping.Classify`, a 3-stage data-driven classifier (packaging, phrases, head noun). `PUT /api/foods/{id}/shop-section` sets it for leaves only; errors `error.food.invalid_shop_section`, `error.food.shop_section_leaf_only`.
- `food.LoadTrees` loads recipe trees in one query per level.

## Plate audit trail

Go migration `00030_plate_events.go` (sqlc reads `schema_patches/00030_plate_events.sql`), `domain/plate/events.go`, repo `adapters/sqlite/plate_event_repo.go` (D20). 00030 also rebuilt `plates` and `cook_sessions` with `AUTOINCREMENT`, so an id never names two rows over time.

Every `plate.Service` mutation writes its events last, in its own unit of work:
- One row per plate it touches: `create` / `restore` (`before_json` null), `update`, or `delete` (`after_json` null), with full plate snapshots in the `SnapshotPlate` shape (its own `plate_id`, sessions by id). `Apply` logs `restore` when `ApplyOptions.Restore` is set (`POST /api/plan/restore`), else `create`.
- One row with `plate_id` NULL per cook session whose row changed (`{id, food_id, cook_date, …}`): fresh and snapshot sessions (`create`), D11 resizes and D13 cook-cell moves (`update`), sessions left without links (`delete`). A tracked session D11 left unchanged writes nothing.
- The explicit session edits (`SetSessionPortions`, `SetCooked`, `AddLeftovers`, `DeleteSession`) always write their session's row and set `cook_session_id` on their plate rows; `SetSessionPortions`/`SetCooked` also log every linked plate.

No FKs, so rows outlive what they describe; there is no read API yet. `plate.Service.Revert` (the undo of an agent change) writes every event with action `undo`, so planning corrections (`UserReplacements`) and `AIRunCorrections` do not read an undo as a user edit. `plate_events` is indexed on `plate_id`, `ai_run_id` (00030) and `cook_session_id` (00038).

**Changes (D13).** `agent.ToolSet.Execute` records each plan-writing call as an `ai_changes` row on a detached ctx (`context.WithoutCancel`), also when the call failed after writing (a `regenerate` whose caller went away waits for its run detached, then records). A change that cannot be saved is returned with `Unrecorded` set: the `change` stream event carries `recorded: false` (`id` 0, `undoable: false`) and the tool result gets `"warning": "change_not_recorded"`; the write stands. `Changes.Undo` of a change that wrote nothing is `400 error.invalid_body` (`ErrInvalidInput`, stays not undone); a `set_availability` change stores the override it left (`availability_before_json.after`) and undo is `409 error.ai.change_stale` when the cell's override differs. `ChatRuns` and `Edits` (hand-written queries over `json_each(ai_changes.run_ids_json)`, sqlc cannot parse it) link a chat run to the runs its changes waited for; a chat run's `edits` include the regenerate run's events within the change's event range.

The actor comes from `domain/actor` in ctx: the HTTP middleware `middleware.Actor` sets `user`, `agent.ToolSet.Execute` sets `agent` with the run's `ai_run_id`, and `actor.From` falls back to `user`.

## Chat agent

Package `domain/agent` (`ToolSet`, loop, prompt `v13`; v13: light intent; v10: do not add up kcal, protein, meat days or keep windows in reasoning, use `apply_changes` with `dry_run`; v9 adds the code execution paragraph; chat `MaxTokens` 16000 (`chatMaxTokens`)). The chat body is `{conversation_id?, message, today?, start}`; `start` must be a shopping day (`Service.CheckStart`, `400 error.plan.invalid_start`; missing `start` is `400 error.invalid_body`, an unparseable date `400 error.ai.invalid_date`). The system prompt renders the window through `planning.RenderPlanSummary` and the issues of `chatIssues` (`chatsummary.go`: `chatView` = the evaluation with the board's H1/H2/H5/H8 plus H3/H4 and the soft issues S1-S3; the prompt states the meat limit, the kcal band and the protein target and says a request is not done while an issue it caused is open unless the user is told why), followed by `chatFacts` (each food on the plan with role and kcal/protein per portion, and kcal per eater per day against the target).

Tools (all JSON shapes are documented in each tool's description, for programmatic tool calling):
- `find_foods` (`find_foods.go`) replaces `list_foods` / `get_food`: `roles[]`, `kinds[]`, `ids[]`, `no_cook`, `diet`, `tags`, `search` (synonym search, below), `max_kcal`, `min_protein`, `sort`, `limit`; each item has id, name, kind, role, `diet_class`, `counts_as_cooking`, `no_cook`, `per_portion` (leaf: typical portion `portion_g` plus `per_100g`), `keep_days`, `last_eaten`. A failing nutrition lookup (cyclic or too deep recipe) never fails the call: the item comes back with `nutrition_complete: false` and zero macros (logged at warn; only a cancelled ctx fails). Macros are resolved after filter, sort and limit unless `max_kcal`, `min_protein` or a kcal/protein sort needs them for all candidates. `ids` combine with the other filters (`roles`, `kinds`, `diet`, `tags`, `search`, `no_cook`); unknown ids go to `missing_ids`.
- `get_plan {from?, to?}` (`plan_tools.go`, replaces `get_plates_range`): cells, sessions, board issues and `evaluation` (days, per-plate and per-component kcal/protein, meat days, issues incl. soft with options; `evaluation_error` when it could not be read).
- `apply_changes {ops[], dry_run}` (`apply_changes.go`) replaces `create_plate`, `add_food_to_plate`, `swap_food`, `update_plate_component`, `remove_plate_component`, `delete_plate`, `set_session_portions`, `set_plate_eaters`, `set_availability`. Ops: `add` (plate by id or date + slot; `session_id` eats from an existing batch; `cook_at {date, slot_id}` cooks a recipe on another cell so it shares that cook cell and adds no H2), `swap`, `set_quantity`, `remove`, `create_plate`, `delete_plate`, `set_portions`, `set_eaters`, `set_availability`. All ops run in one `Services.Tx` unit of work through `plate.Service`; a failing op names itself and rolls the batch back; `dry_run` ends the transaction with `errDryRun` so nothing is written (also not `ai_changes`), and is recorded as a `dry_run` evaluation step. The result is `{dry_run, applied, after}`: `after` has the plates (kcal and protein per eater, per component `component_details` with `plate_component_id`) and sessions touched, the `Evaluate` days of the touched dates (a `cook_at` op's cook day included; ops dated outside the chat window are evaluated in the 7-day window that holds them, `issues_checked` is false with a reason only for a touched date no evaluated window covers), meat days, and the issues new / resolved / total_open (hard and soft, options included) against the evaluation before the call (`Services.State`), all in the compact form (see Plan generation). **Dry run ids are provisional:** a dry run rolls back, so after the rollback `markProvisional` walks the whole result (`applied`, `after.plates`, `component_details`, `after.sessions`, the issue deltas and each option's `op`) and replaces every `plate_id` / `plate_component_id` / `session_id` whose row no longer exists (looked up once per row; a failing lookup counts as present, so rows outside the window or sessions without components are never mislabeled) by `"provisional": true`; an option whose `op` used such an id is marked provisional too. `dry_run_note` says so and tells the model to send the full op list again with `dry_run` false (ops cannot reference earlier ops of a batch).
- `confirm`, `unlock`, `regenerate` (plan_tools.go) and the preset tools are unchanged; the old single-write tools no longer exist.

**Decisions (agent tools v2).** One `ai_changes` row per `apply_changes` call (`text_key` `apply_changes`, params `{count, ops}`; `ops` is one `{op, food?, to?, date?, slot_id?, slot_key?, mode?, portions?, amount?, unit?, eaters?}` per op and the frontend composes the localized line, capped at 3 ops; older rows carry a ready `summary`), not per op: the loop, the stream and the frontend carry one change per tool call; undo is per call. At most one `set_availability` op per call, because a change stores one cell's `availability_before`. Older conversations keep their per-tool text keys (`set_session_portions`, ...), so the frontend still renders them. No-cook detection is the derived `planning.NoCook` (see Plan generation). Above-band kcal issues carry no options.

- **Tool results and search.** Plan-writing tools return an `after` block (`effects.go`, `withEffect`; `apply_changes` builds its own combined one): the affected plates (date, slot, components with roles), the cook sessions (portions, consumed, surplus, warnings such as `deficit`) and the checker issues this write made new or resolved (`issues: {new, resolved, total_open}`, each list capped at 10 with `new_more`/`resolved_more`; the window's issues are snapshotted before the tool runs, see `withIssueBaseline`). When they could not be read it says `issues_checked: false` with `issues_unchecked_reason`, never an empty list. The model need not call `get_plan` to verify. `apply_changes` `set_portions` refuses (`ErrInvalidInput`, numbers in the message) portions below what the linked plates eat or frozen portions below the frozen consumption (spec §3.4, H3: a silent deficit is a hard-rule violation the model need not relay). `find_foods` filters by `roles`, `diet` and the other filters and searches names and tags in Go (`searchPage`): case and umlaut folded, with the en/de synonym table in `domain/diet/search.go` (`SearchAlternatives`, `MatchesWord`): the English member of a group matches a whole word (plural allowed: `pea` not Peanut, `egg` not Eggplant), the German members match word starts (`reis` finds Reispfanne, not Preiselbeeren). Component results carry `name` and `role`.
- **Draft guard (D5-D7).** Under `actor.Agent`, `plate.Service` (`plate/guard.go`) refuses writes to confirmed rows with `domain.ErrRowConfirmed` (`error.plan.row_confirmed`) before writing; `confirm`/`unlock` are exempt. A new plate-writing op must call `guardDate`/`guardPlateDate` (`agent/tools.go`; past dates are `error.ai.past_date`) and must never work around the row guard. Tests pin today with `agent.WithToday` (`export_test.go`).
- **Unlock is two-phase (D6).** `agent/unlocks.go` keeps an in-memory map (conversation id + closure, 30 min TTL, single use). The first `unlock` call previews the closure (`plate.Service.BatchClosure`, read-only), returns `409 error.ai.unlock_needs_user` and the loop emits `unlock_request`; only a call in a later turn (turn counter in ctx) unlocks. A restart loses the map.
- **`regenerate` waits (D8).** It starts a run through `planning.Service` and blocks on `planning.Service.Await(ctx, id)` (a per-run done channel in `Progress`); a cancelled ctx returns at once and the run goes on. Its writes run under the generator actor with the regenerate run's id.
- **`ai_changes` (00037; D13).** One row per plan-writing tool call (one per `apply_changes` call, not per op): `run_id`, `step_seq`, `tool`, `text_key` + `params_json` (the frontend renders `assistant.change.<text_key>`; params carry names, dates, `slot` as a name key, portions, eaters), `run_ids_json` (the chat run plus a regenerate run), `dates_json`, `plate_ids_json`, `session_ids_json`, `first_event_id`/`last_event_id` (the plate-event range), `availability_before_json` (the cell set_availability changed), `undone_at`. `ToolSet.Execute` returns `(*Change)`; handlers call `noteChange`/`noteRun`/`noteCell`; the loop emits `change` after `tool_result`, and `GET /api/ai/conversations/{id}` includes `changes`.
- **Undo (`POST /api/ai/changes/{id}/undo`).** Runs as `user` (the draft guard would block `agent`), returns `{plate_ids, session_ids}`; `409 error.ai.change_undone` when already undone, `error.ai.change_confirmed` when a plate or session of the change is confirmed now (checked first; `confirm` changes are exempt; the conversation read model and `change` events carry `undo_blocked: "confirmed"|null`), `error.ai.change_stale` when any foreign event touched the rows after `first_event_id`. Known limits: `grams_source` is not restored; an availability undo overwrites a later manual change of that cell.
- **Run attribution (D11-D12).** Chat runs follow the outcome of drafts they edited (`AgentRunsOfRows`, bounded by the last undone accept/confirm or unlock) and of runs they started (`ChatRunsOfRun` through `ai_changes.run_ids_json`); the run list/detail `edits` field is described in AI run log. `plate_changed` no longer exists.
- **Fake provider turns.** Besides plain turns (the default sequence), a script turn may carry `match_user` (case-insensitive substring of the latest user text; first match in script order) and `for_tool` (used when `ToolChoice` names that tool). Each form has its own cursor; a turn with both counts as `for_tool`. E2E uses it to script chat and generation in one file (`frontend/e2e/fixtures/chat-scripts/`).
- **Fake search turns.** A turn may also carry `search_results` (`[{url,title}]`), `web_search_requests` (the billed count, recorded on the step) and `stop_reason: "pause_turn"` (the call returns the paused turn and advances the cursor, so the next call is the continuation). The script-level `capabilities.web_search` (default false) is what `llm.Capabilities.WebSearch` answers. Server blocks replayed as `{type: "server", raw}` are accepted. The fake records requests so tests can assert the research prompt and the replayed blocks. `chat-scripts/discovery.json` is the template for discovery runs (see Discovery).

## Programmatic tool calling

Anthropic only (docs: `agents-and-tools/tool-use/programmatic-tool-calling`): the model writes Python in Anthropic's code execution container that calls our tools, so fan-out and "try several drafts, keep the best" cost one model turn.

- **Request.** `llm.Request.CodeExecution` (opt-in) and `Container`; `llm.Tool.AllowedCallers` (`llm.CallerDirect`, `llm.CallerCodeExecution` = `code_execution_20260120`). The Anthropic adapter sends `{"type":"code_execution_20260120","name":"code_execution"}` first in `tools`, `allowed_callers` on the tools that list it and `container` only when `plan` says the model may: `capabilities.code_execution.supported` from the Models API (the top-level capability, not `server_tools.code_execution`; Haiku 4.5 accepts the tool but not this), no forced `tool_choice`, no earlier rejection. Otherwise it sends none of it and records why in `sent.fallbacks` (`code_execution_unsupported_by_model`, `code_execution_with_tool_choice`, `no_code_callable_tools`, `capability_unknown`, `capability_lookup_failed: …`, `code_execution_rejected_by_model`). A 400 naming `code_execution`, `allowed_callers` or `programmatic` is retried once without (attempt reason `code_execution_rejected_400`) and remembered per model; the retry strips the code blocks from the replayed history. **A request that does not send the code tool (setting off, capability gone, rejected) replays the history without code blocks** (`llm.StripCodeBlocks`: `server_tool_use` of code execution, its result blocks, the code-called `tool_use` and their `tool_result`; recorded as fallback `code_blocks_stripped`): the docs do not say whether the tool definition is needed to replay them, and a history without them is always valid. Web search blocks are not touched. A 400 naming the container while no programmatic call is pending (an expired container) is retried once without `container` (`container_rejected_400`, fallback `container_dropped_after_400`); with a call pending the continuation requires it, so that 400 is the caller's. **`anthropic-version` stays `2023-06-01`**: the 2026-10-21 version changes sampling parameters, assistant documents and deprecated fields; programmatic tool calling is not version-gated (decision from the docs; not verified live). The 400 fallback above is the safety net and its error body is stored on the failed step.
- **Response.** `llm.Response.ContainerID` / `ContainerExpiresAt` (message_start and message_delta `container`); `ContentBlock.Caller` on a `tool_use` (`{type: direct}` or `{type: code_execution_20260120, tool_id}`, replayed on later requests). `server_tool_use` and `code_execution_tool_result` blocks replay as `server` blocks. A reply that pauses on code-called tools has `stop_reason: tool_use`; the continuation must carry `container` and answer with a user message holding only `tool_result` blocks (the loops already answer every call with results only). `pause_turn` with no tool call makes the chat loop and the planner chooser resend the paused turn as it is (no repair used).
- **Loops.** The chat loop (`RunRequest.CodeExecution`, `Container`, `SaveContainer`) keeps the container for the turn and stores it per conversation (`ai_conversations.container_id` / `container_expires_at`, migration 00044), reused by the next turn while `container_expires_at` is in the future (the expiry is refreshed from every reply; an expired one is logged as `agent.container.expired` and the turn starts without it). `Service.Chat` opts in from `ai.programmatic_tools`; off also strips `allowed_callers` from the tools. Every tool call runs with `llm.WithCaller(ctx, caller)`; `ToolSet.Execute` refuses a code call of a tool that is not `CodeCallable` (`ErrCodeCallRefused`; `allowed_callers` is guidance, not a boundary). Code-callable: `find_foods`, `get_plan`, `apply_changes`; **`apply_changes` from code must set `dry_run: true`**, otherwise `ErrCodeCallRefused`, so writes stay direct and the final change set is one visible decision. The planner chooser (`LLMChooser.WithProgrammatic`) offers `evaluate_plan` to code (`maxCodeEvaluations` = 30 per run, direct ones keep `maxEvaluations`) and keeps the run's container; `submit_plan` is direct only: a code-called `submit_plan` is answered with an error and never counts as the submission.
- **Bounds.** A script that awaits one tool call at a time is one request per call, so requests that only continue code (the reply's tool calls all come from code, or a `pause_turn` resend) are not model turns. Model turns keep their caps (planner `maxModelCalls`, chat `MaxIterations`); code continuations have their own (planner `maxCodeEvaluations`, chat `MaxCodeContinuations` = 40), and a hard total per run (planner `maxRequests`, chat `MaxRequests`). Planner: at a bound the run ends with the last submitted proposal and a run note, or `error.ai.invalid_plan`, and logs `plan.run.stopped`. Chat: at `MaxCodeContinuations` the pending code-called calls are answered with an error ("stop calling tools") so the model closes the turn with a message (log `agent.loop.code_limit`); at `MaxRequests` or `MaxIterations` the turn fails with `error.ai.iterations_exceeded`.
- **Output cut-off.** A reply with `stop_reason` `max_tokens` never executes its tool calls (their input may be cut; an empty `evaluate_plan` once evaluated an empty plan). Each `tool_use` is answered with an `is_error` tool result saying the reply was cut off, nothing was run, and to keep reasoning short and let the tools compute (planner: put the draft into `evaluate_plan`; chat: `apply_changes` with `dry_run`). It is a model turn under the existing bounds (`maxModelCalls`, `MaxIterations`), not a repair or attempt; a cut reply that only holds code-called tool calls counts as a model turn too (bounded: chat 20 x 16000 tokens, planner 14 x 32000). A cut tool input arrives as a JSON string of the partial text: it is replayed as `{}` (`llm.ObjectInput`; both adapters and the stored chat history), while the `is_error` tool step keeps the raw text in `args_json` and the `llm_call` step's `response_json` keeps it as received. Recorded as `is_error` tool steps (result `{"error": ...}`), a run note in the planner (once) and the log lines `plan.run.cutoff` / `agent.loop.cutoff` with `model_seq` (the cut reply's step) and `tool_seqs` (every answered call's step). A text-only reply cut at `max_tokens` still ends a chat turn as a normal final answer.
- **Stored conversation.** The chat loop buffers the messages of an open code turn (`llm.CodeTurnOpen`: a code server block without its result block) and stores them once the turn closes. If the turn ends first (failure, cancel, cap), the stored remainder omits the code blocks, the code-called tool calls and their results (`llm.StripCodeBlocks`), so the next request never continues from unanswered programmatic calls (a text message there is a 400). Earlier messages are never rewritten.
- **Logging.** See AI run log: `code_execution` steps, `caller` columns, `ai_runs.container_id`, `request_json.sent`.

## Prompt caching (Anthropic)

`encodeRequest` puts a 5 minute `cache_control` breakpoint on the system prompt and on the last tool, and, only when `llm.Request.CacheTail` is set (the chat agent loop and the planner's LLM chooser, which resend their history; one-shot calls (importer, lookups, discovery) would pay the 1.25x write and never read it), on the last block of the last message (3 of the 4 allowed), so a request resends its history as a cache read instead of fresh input; before, only system and tools were cached and every large tool result (`evaluate_plan`, `apply_changes`, `get_plan`) was billed as uncached input on every later turn. Each breakpoint reads back from an earlier request's write, and the 20-block lookback is not a problem here because a turn adds one assistant message and one user message (parallel tool calls collapse to one position). A server block (verbatim thinking, code execution, web search) cannot carry the marker, so the breakpoint goes on the last other block of that message (`tailIndex` picks the block, `tailCacheable` reports it, and decides what `llm.Effective.CacheBreakpoints` reports: `system`, `tools`, `messages`). Check the effect with `usage.cache_read_input_tokens` of the run steps.

Chat: `before` first (from the state the prompt was built from) and `after` last, also on error or cancel (read again on a detached ctx; a state that cannot be built stores an `is_error` step with the cause). Generate and regenerate: `attempt` for the merged proposal of every readable LLM attempt (n = the attempt, 0 = first reply) and one closing step on a detached ctx: `after` once the plan was saved, evaluated from a re-read of the window with the same builder (persisted plate ids, as the board will show it), or, when the chooser fails, the run times out, the save fails (plan changed) or the run panics, `final_proposal` with `status` (`error`, `timeout`, `panic`) and `stage` (`choosing`, `saving`, ...) evaluated on the base plan merged with the chooser's last proposal (the LLM chooser returns its last repairable proposal with a provider error; none: the unchanged plan). A run that fails while resolving the base plan has no evaluation. The target is the run's target (chat: every cell of the window, `planning.WindowTarget`). It uses the same state builders as the board (`TestStateParity_BoardAndBuilder`).
  - `plan.context` (`planning/contextlog.go`, first step of the chooser; args `{"chooser"}`): `chooser`, window and today, the settings and profile targets the run works under, `explore_quota`, `target_cells` / `open_cells`, `short_days` (planned meals < meals, scaled kcal target or null without a profile kcal target; from `dayAccounts`), `avoid`, `avoid_batches`, `eaters_by_date` (the per-day eaters override, a regenerate's kept eaters included) and `side` (a side swap: replaced food, role, cook date/slot, portions, frozen portions, the plates eating it), `plates` and `sessions` {total, fixed (confirmed or outside the target)}, `candidate_ids` (what the chooser may use) and `excluded` [{id, name, reason}] with reasons `replaced_by_target` (the rows a regenerate replaces), `diet_incompatible` (both from `eligibleSplit`, the filter the chooser's `eligible()` uses), `side_swap_other_role` and (LLM only) `token_budget` (the 40k-token trim of `RenderPrompt`). `excluded` is sorted by id. A run with no open cell has no chooser and so no such step.
  - `heuristic.choices` (heuristic runs): per plate placed `{date, slot_id, foods, reason}` with reason `cook_new`, `leftover_of_new_batch`, `leftover_fixed_batch`, `leftover_proposed_batch`, `leftover_grown_batch`, `frozen_portion`, `side_swap` (the single choice of a side-swap run), and for a cell left empty `left_empty_no_main` / `left_empty_cook_cap`. Bump `HeuristicVersion` when a reason code's meaning changes.
- **Programmatic tool calling (00044).** `ai_run_steps.type` also allows `code_execution`, recorded by the metered client for every code execution result in a reply (`airun/codeexec.go`): `name` is the server tool (`code_execution`), `args_json` the code, `result_json` `{tool_use_id, container_id, result_type, stdout, stderr, return_code, error_code}` (capped like every tool result, 256 KiB), `is_error` for a non-zero return code, an error result or `TimeoutError` in stderr (a pending-call timeout), `status` (`pending` when the code was issued, `completed`, or `unfinished` when the run ended first; the step is written when the code is issued and updated when its result arrives or the run finishes), `code_execution_requests` (the reply's `usage.server_tool_use.code_execution_requests`, `llm.Usage.CodeExecutionRequests`), `duration_ms` from the reply that carried the code to the end of the reply that carried its result (so it includes the pauses for tool results). A `tool_call` step (and the planner's `plan.evaluation` steps) made on a tool call carries `caller` (`direct` | `code_execution`) and `caller_tool_id` (the code's server tool use id; NULL for steps the code writes itself). A code-called tool's result is not part of the model's context (the API keeps it inside the code), so that step's `result_json` is its only copy. `ai_runs.container_id` is the run's last container; `request_json.sent` adds `code_execution` (on/off), `code_tools` (tools sent with a code caller) and `container` (id sent); `response_json.container_id` the reply's. `ai.tool.call` carries `caller`, `caller_tool_id`, `container_id`; `ai.llm.call` carries `container_id`, `sent_code_execution`, `sent_code_tools`; `ai.code.execution` logs each code step (return code, byte counts). The run detail API shows `container_id`, and per step `caller` and `caller_tool_id`.
- **`ai_prompts`** — system prompt text stored once per distinct hash. Every distinct system prompt of a run is stored (a lookup has two: translate and pick-best); `ai_runs.prompt_hash` is the first call's.
- **`ai_tool_schemas`** — tool definitions (`json`, a `[]llm.Tool`) stored once per distinct hash.
- **Replay.** Call *i*'s request is call *i−1*'s messages cut to `message_offset` plus call *i*'s `messages`, the prompt by `system_hash`, the tools by `tools_hash`, `temperature`, `max_tokens` and the step's `name` as model. Callers append the assistant reply to their history themselves, so replies are already in the next delta; never insert `response_json` into a reconstruction. `domain/airun/replay_test.go` (`reconstruct`) is the reference.
- **Retention.** At startup and after a finished run (at most once per hour; both in a goroutine, deleting in batches of 500; `Recorder.Wait` waits for them and stops new ones from starting) the steps of runs started more than `ai.run_retention_days` days ago (setting, default 180) are deleted. `ai_runs`, `ai_prompts` and `ai_tool_schemas` rows stay. There is no background scheduler; prune failures are logged at warn and not retried for an hour.
- **Cost is not stored.** `airun.Cost(model, provider, tokens, overrides)` (`cost.go`) computes it on read: an `ai.price_overrides` entry for the exact model id wins, else the built-in table entry with the longest model-id prefix (`PricesAsOf`, sources cited next to the table). Missing cache prices default to 0.1× / 1.25× of the input price (0.5× / 0 for OpenAI, whose input count includes the cached tokens, which are subtracted). An unpriced model is `nil` ("cost unknown"); a run without tokens costs 0. slog lines all carry `run_id`, `request_id` and (chat) `conversation_id` (`Run.LogAttrs`): `ai.run.start` / `ai.run.end` (with duration, reasoning, `error_key`), `ai.llm.call` per model call (step seq, provider, requested and served model, duration, ttft, all token kinds, stop reason, tool choice, effective max_tokens, request/response bytes; on failure the provider status and error type, never the key or text; WARN), `ai.tool.call` per tool call (tool, duration, `is_error`, `error_key`, `args` reduced to numbers, dates, ids and the short `search`/`kind`/`role`/`diet`/`sort` filter values), `ai.llm.body` at debug (bodies cut to 2000 chars), `plan.run.stage` per generation stage (heuristic runs too: `stage`, `elapsed_ms`, checker counts `by_rule`/`by_code`, saved `plates`, `routine_plates` and `proposal_sessions` (the chooser's; the run API's `counts.sessions` are the persisted ones, routine plates' included), a final `done` line with status and score), `plan.run.attempt` per LLM chooser attempt (on the service logger: counts, `violation_list` as `rule.code@date/slotN plate= session= {params}` capped at 20, or `parse_error` of an unreadable reply; each attempt is also a `plan.attempt` tool step of the run with the same record), `discovery.run.stage` per discovery stage, `import.stage` per import stage (`fetch`, `parse_jsonld`, `fallback` with `step`/`attempt`/`outcome`/`parse_error`/`retry_reason`, `resolve`; the fallback lines carry the run's ids), `anthropic.request.retry` (a retried 400 with its reason and request id), `settings.models.failed` (a failed key check: provider, status, error type, request id; never the key or body), `ratelimit.rejected` (the app's own limiter: path, client, limit). `ai.llm.call` also carries `sent_tool_choice`, `sent_web_search`, `sent_temperature`, `fallbacks`, and on failure `provider_message` (cut to 300), `provider_request_id`, `provider_rate_limit` (`retry-after`/`ratelimit` headers), `after_first_token`, `partial`, `retry_reason`. The debug line `ai.llm.body` may contain prompt and reply text; nothing at info or above does. There is no retry layer for 429/529: they end the call and are logged with their headers. `started_at` of a step is `2006-01-02 15:04:05.000`, unlike `timeLayout` elsewhere (the run detail re-formats it as RFC3339 with ms). `thinking_chars` counts runes of thinking text only (redacted thinking is 0).
- **Read API** (`handlers/ai_runs.go`, `airun.Insights`, repo `ai_run_insights_repo.go`; one query per aggregate):
  - `GET /api/ai/runs?kind&from&to&cursor&limit` (50, max 200) — newest first, `next_cursor` is the last id of the page; items carry `tokens`, `cost_estimate_usd`, `score`, `outcome`, `correction_rate`, `edits`.
  - `GET /api/ai/runs/{id}` — `duration_ms`, `tokens.reasoning`, per step `started_at`, `ttft_ms`, `tokens.{cache_read,cache_write,reasoning}`, `thinking_chars`, `served_model`, `provider_request_id`; plus `app_version`, `scope`, `instruction`, `notes`, `violations`, `error_key`, `prompt_text` and `steps` in seq order; a step's `args`/`result` are text: a tool step's come whole (only the 256 KiB store cap applies, so a cut one is not valid JSON and sets `*_truncated`), an llm_call's are its request/response JSON cut to 8192 characters (`*_truncated`).
  - `GET /api/ai/insights?from&to&bucket=week` (default: the last 12 weeks) — Monday weeks with `runs`, `accepted` (incl. partially), `discarded`, `correction_rate`, `cost_usd` (priced runs), `cost_per_accepted`, `unpriced_runs`; `by_version` groups by kind, prompt version and model with `tokens`, `edits` (chat groups only), `score_avg` (numeric leaves of `score_json`, dotted keys, without per-date entries such as `cook_occasions.per_day.<date>`) and violation counts by rule.
  - `GET /api/ai/prices?model=` (default: the configured model) — `{model, price|null, source: builtin|override|none, as_of}`.
  - Correction rate (D24, sqlc `AIRunCorrections`): plates a run's `generator` or `agent` `create` events made, and how many of them got a `user` `update`/`delete`, or an `agent` one from another run, before the plate's first `accept`/`confirm` event.
  - Edits (sqlc `AIRunEdits`): the distinct plates and sessions an agent run wrote events for; a session edit counts once as its session (its linked plates' events carry `cook_session_id`). Null for a run without agent events.
  - Outcomes: accept, discard, unaccept and restore also move the agent runs that wrote an event for the closure's rows (`RunOutcomes.AgentRuns`), so a chat that only edited a generated draft follows it.
- **Tool choice.** `llm.Request.ToolChoice` forces a tool: Anthropic sends `tool_choice: {type: tool, name}`, OpenAI `{type: function, function: {name}}`; both send `temperature` only when it is > 0. The metered client stores it as `tool_choice` in `request_json`. The fake client's script already replays scripted `tool_use` turns.
- **LLM chooser** (`planning/llmchooser.go`, prompt `planning/prompt.go`, D11–D14): one forced `submit_plan` call per attempt (temperature 0.4, max_tokens 32000, streaming) under the run's ctx, so each call is a step; a proposal with violations or an unreadable reply goes back as a tool result, at most twice (`repair_attempts`, stage `repairing`). The feedback (`planning/repair.go`) explains each violation in words with the numbers (consumption per link, keep days and last allowed date, cook cells of an H2 day), the cells and keys, and a fix; a reply identical to the previous one is called out, and a lunch or dinner plate without a main sends the plan back as well (`suitability.go`: the slot kind is the slot's `kind` (`light` or `meal`, migration 00042: default `meal`, `slot.breakfast` and `slot.snack` set to `light`; read through `State.SlotKind`, never from name, position or routine cells); roles that count as a main per meal kind are data in `mainRoles`: a standalone recipe is a breakfast only). A side swap whose new side changes the role is sent back too. Calories (`kcal.go`): `planning.DayKcals(State, Target)` is the pure per-day account (kcal per person against the target scaled to the planned non-`none` meals, also for days with nothing proposed); the chooser never repairs a kcal gap (the user picks options for gaps later): a day below 70 % of its target is one run-notes line per run ("Below target: Mon −620 kcal, Wed −410 kcal"). A side swap with no other side of the replaced role gets every side as candidate and the prompt says so (no role advisory then). Before checking, `autofix` grows a proposed session's portions (and frozen portions, for a freezable recipe within the freezer limit) to cover its plates; the change is in the attempt's `autofix` list and in the next feedback. Violations left after that are persisted (`partial`); a provider failure ends the run `error.ai.provider_error`, no readable reply at all `error.ai.invalid_plan`. A request without `chooser` uses the LLM when a provider resolves and the heuristic when none is configured; a configured provider that fails to resolve is `502 error.ai.provider_error` (logged), never a silent fallback. The prompt keeps within 40 k estimated tokens (chars / 4) by leaving out candidates. E2E fixtures: `frontend/e2e/fixtures/chat-scripts/generate-week.json` (a template; placeholders in its `_comment`) and `generate-week-error.json`.

- **Generation runs** (`planning.Service`): a run outlives its request but not the process. `Shutdown(ctx)` (called from `main.go`, bounded to 5 s) refuses new runs and cancels the running ones, which end `error` / `error.server`. A run out of time ends `error.plan.timeout`; saving has its own 30 s budget, so a proposal ready at the deadline is still written. A save that finds the plan changed while the run chose (a replaced draft confirmed or gone, a target cell taken or No plate, a linked session gone) ends `error.plan.changed_during_run` and writes nothing. The window's reservation is freed by deferred calls, even after a panic (logged with its stack). `GET /api/plan/runs/{id}` reports a `running` row the in-memory registry lacks as `error` / `error.server`. Plate outcomes (D25): a restore of drafts (`POST /api/plan/restore`, the Undo of discard) records `restored`, which reopens a discarded run (discarded → open, partially_accepted → accepted).
- **Mid-week re-plan** (`planning/replan.go`, `plate.Service.RemovePlates(plate.Removal)`): the preview and the re-plan share one scan. An uncooked batch whose cook plate goes moves its cook to its earliest remaining plate only when every remaining plate lies in [from, to], none eats from the freezer, and that day has a free cooking occasion (`plan.max_cook_occasions_per_day`, routine cells aside); otherwise the batch is dropped with every component eating it, in or outside the range, and plates left empty go. The preview lists `dropped` plates (`{session_id, food_name, plate_id, date, slot_id, confirmed}`) and `moved` batches (`{session_id, food_name, cook_date, cook_slot_id}`), and every confirmed plate that goes or loses a component is in `confirmed_affected` (so it needs `unlock_confirmed`). `POST /api/plan/replan` returns `regenerate_error` (a message key) when `regenerate` was asked for but its run did not start; the removal stands.

## Coding Rules

- **`errors.Is()`, never `==`** for sentinel errors. Wrapped errors break `==` silently.
- **Domain validation in the service, not the DB.** DB constraints are a safety net only.
- **Sanitize FTS5 input.** Pass user search strings through `sanitizeFTS5()` before MATCH.
- **Use sqlc-generated functions, not raw SQL.** Change query annotations and regenerate if needed.
- **`testhelper.NewTestDB()` must mirror production config** (same pragmas, `SetMaxOpenConns(1)`, etc).

## Testing

**Unit tests:** pure, no DB, no HTTP. Use fakes from `adapters/fake/`.

**Adapter tests:** real SQLite via `testhelper.NewTestDB()`. Never mock the database.

**Migration tests:** `migration_000XX_test.go` in `adapters/sqlite/` — test data shape before and after.

### Coverage Requirements

Every feature must cover happy path **and** edge cases before it's complete:

- Validation: empty/missing required fields, invalid enums, out-of-range numbers, boundary values
- Conflicts: duplicate names, update/delete non-existent, in-use references
- Input sanitization: FTS operators, SQL-sensitive chars, unicode
- Nullable roundtrips: create with value → update to null → verify null
- HTTP edge cases: malformed JSON, non-numeric IDs, invalid query params

## Worktrees

Inside `.claude/worktrees/*`, prefix Go commands with `GOWORK=off` (e.g. `GOWORK=off go test ./...`). The root `go.work` created by `mise run lsp` lists only the main checkout's `./backend`, so without it Go fails with "directory prefix . does not contain modules listed in go.work".

## SQLite Gotchas

- Pragmas are per-connection. `sql.DB` pools — use `SetMaxOpenConns(1)` so all queries share WAL + `busy_timeout`.
- Timestamps: stored as `TEXT` via `datetime('now')`, Go parse layout `"2006-01-02 15:04:05"`, serialize as RFC3339 in API responses.
